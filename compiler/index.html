Why this exists: one pipeline, many jobs

A compiler is a program that reads a program in one language and writes an equivalent program in another language. “Equivalent” means the output program computes the same answers and has the same observable effects. A compiler also has to reject bad programs with useful errors. That is the whole subject. The syllabus is a list of the jobs inside that translation, in the order the data meets them.

Two side structures run alongside every stage. The symbol table remembers what names mean: type, scope, storage, and sometimes the generated location. The error handler records what went wrong and tries to keep going so the programmer sees more than one error per compile. The symbol table is the glue between lexical analysis, parsing, type checking, and runtime storage; that is why it appears in several sections below.

Front end: understand the program. Lexing, parsing, semantic analysis, and IR generation. It is source-language dependent and largely machine independent. Its output is a checked intermediate representation.
Back end: make it run. Optimization and code generation. It is target-machine dependent. Its input is the IR; its output is instructions, registers, and memory layout. Optimization often sits in the middle, sharing both worlds.

The syllabus names seven things: lexical analysis, parsing, syntax-directed translation, runtime environments, intermediate code generation, local optimization, and data-flow analyses (constant propagation, liveness, common-subexpression elimination). In pipeline order, they are not seven separate subjects. They are seven answers to one question: what does the next stage need to know, and how can we compute it without losing meaning?

The one-sentence map. Characters become tokens; tokens become trees; trees get meaning; meaning becomes intermediate code; intermediate code gets optimized using facts; the facts come from data-flow analysis; and the runtime environment explains where every value actually lives while the program runs.

The learning order, and why it is this order

  1. The pipeline first. You need to know what each stage receives and hands on before studying any one stage.
  2. Lexical analysis. It is the smallest complete translation problem: regular expressions in, tokens out. It teaches states, nondeterminism, and determinization without grammar complexity.
  3. Grammars and trees. Parsing needs a precise way to say what a legal program looks like. Derivations and ambiguity are that language.
  4. Top-down parsing. The most direct parser: look at the next token, predict a production, recurse. It motivates FIRST, FOLLOW, left-recursion removal, and left factoring.
  5. Bottom-up parsing. The industrial-strength parser: shift tokens, reduce handles, and build an LR automaton. It reuses the grammar ideas and adds lookahead.
  6. Syntax-directed translation. Once the tree exists, attach values and types to it. This is where parsing becomes compiling.
  7. Intermediate code and type checking. Turn the annotated tree into a small, machine-independent instruction set. Type checking keeps the operations meaningful.
  8. Runtime environments. Before optimizing, know where variables, parameters, and frames live at run time.
  9. Basic blocks and local optimization. The first optimization scale: one straight-line block, then a graph of blocks.
  10. Data-flow analysis. The general machine for facts that must be true at many program points. It powers constant propagation, liveness, and global common-subexpression elimination.
  11. The toolkit. A numbered set of moves to recall under exam pressure.
Heads-up: “phase” is not “pass.” A phase is a logical job (lexing, parsing, optimization). A pass is one complete read of the input. A compiler can combine several phases in one pass, or split one phase across several passes. Exam questions often say “phase” when they mean the logical job; do not assume a separate program or a separate traversal.

1. The compiler as a pipeline

Start with the smallest true picture. A compiler has an analysis half that figures out what the source means, and a synthesis half that builds the target. The boundary is an intermediate representation (IR): a program form that is simpler than the source but not yet tied to a machine.

“Semantic analysis” is not one algorithm. It is the collection of checks that need more than syntax: names are declared, types match, functions are called with the right number of arguments, `break` is inside a loop, and so on. Syntax-directed translation is the usual way to organize those checks: walk the tree and compute attributes such as type, value, or generated code.

1.2 One statement through every stage

Take the classic assignment

\[ \texttt{position} = \texttt{initial} + \texttt{rate} * 60 \]

Assume position, initial, and rate are floating-point variables and 60 is an integer constant. The lexer turns the characters into tokens. A token is a pair: a class and an attribute. The attribute tells which identifier or which number.

Tokens. <id, 1> <assign> <id, 2> <plus> <id, 3> <times> <num, 60>. The numbers 1, 2, 3 are symbol-table indices, not values. The lexer does not know or care that the statement is an assignment; it only knows the word classes.

The parser groups the tokens according to the grammar. Multiplication binds tighter than addition, so the tree is not a flat list. It records the intended grouping:

          =
        /   \
     id1     +
            / \
         id2   *
              / \
           id3   60

The root is the assignment. Its left child is the place being assigned; its right child is the expression. The expression’s top operator is +, and its right operand is the product. This tree is already a small intermediate form: the grouping is explicit, and the original parentheses and precedence rules are no longer needed.

Semantic analysis walks the tree with the symbol table. It discovers that id1, id2, and id3 are floats, while 60 is an integer. Most languages convert the integer to a float before multiplying. The tree gains an explicit conversion node, often written inttofloat.

\[ \texttt{id1} = \texttt{id2} + \texttt{id3} * \texttt{inttofloat}(60) \]

Intermediate code generation makes every operation and temporary explicit. A common form is three-address code: each instruction has at most one operator and at most three names.

t1 = inttofloat(60)
t2 = id3 * t1
t3 = id2 + t2
id1 = t3

The optimizer notices that 60 can be converted at compile time, and that t1 is used once. It can fold the conversion and shorten the sequence:

t1 = id3 * 60.0
id1 = id2 + t1

Finally, code generation maps the temporaries to registers and picks instructions. One possible target sequence is:

LDF   R2, id3
MULF  R2, R2, #60.0
LDF   R1, id2
ADDF  R1, R1, R2
STF   id1, R1

The exact instructions do not matter for the syllabus. The shape does: characters → tokens → tree → typed tree → IR → cheaper IR → target code. Each arrow loses some source-level convenience and gains some machine-level explicitness.

1.3 Why split the job into phases?

  • Different grammars for different jobs. Tokens are regular: identifiers, numbers, and punctuation can be described by finite automata. Program structure is context-free: nested parentheses, blocks, and expressions need a stack. Types and declarations need context-sensitive checks. Using a parser for characters would be wasteful; using a finite automaton for nested blocks is impossible.
  • Portability. A front end for language L plus a back end for machine M gives a compiler for L on M. With \(n\) languages and \(m\) machines, separate front ends and back ends need \(n+m\) components instead of \(n \times m\) whole compilers. The IR is the contract between them.
  • Optimization needs a machine-independent form. It is easier to reason about “this expression is computed twice” in IR than in raw assembly, and easier to retarget the result.
  • Errors are easier to explain at the right level. “Unterminated string” is a lexical error. “Missing `)`” is a syntax error. “Adding a string to an integer” is a semantic error. Each phase has the context to say what went wrong.
Compiler versus interpreter. A compiler translates the whole program before it runs; an interpreter executes the source (or an internal form) directly. The boundary is blurry: bytecode compilers translate to an IR, and a virtual machine interprets it; just-in-time compilers translate hot paths to machine code while the program runs. The analysis phases are similar; the difference is when translation happens and how much is done ahead of time.
Key. The compiler’s job is meaning-preserving translation. The front end recovers meaning; the back end preserves it while changing the form. The IR is the handoff point, and the symbol table is the shared memory of names.
Heads-up. “Optimization” never means “change what the program does.” It means “produce a program with the same observable behavior that runs faster or uses less space.” If a transformation changes results, error behavior, or side effects, it is a bug, not an optimization. Languages with undefined behavior complicate this: the compiler may assume the undefined case never happens.

2. Lexical analysis: characters to tokens

The lexer is the first phase that actually reads the source. Its job is narrow and complete: turn a stream of characters into a stream of tokens, discard layout that has no meaning (spaces, tabs, newlines, comments), track the line number for error messages, and put identifiers into the symbol table. It does not build a tree and it does not check types.

2.1 Token, lexeme, pattern: three words that exams mix up

WordMeaningExample

For the source fragment

if (count > 10) count = 0;

the lexer might emit

<if> <lparen> <id, count> <gt> <num, 10> <rparen>
<id, count> <assign> <num, 0> <semicolon>

The attribute is the extra information the parser will need later. For an identifier, the attribute is usually a pointer into the symbol table; for a number, the numeric value (and sometimes the literal text, to preserve precision and formatting). Keywords and punctuation usually need no attribute: their token class already says everything.

Why the lexer is a separate phase. Token rules are regular, so a finite automaton can recognize them in time proportional to the input, with no stack and very little memory. If the parser had to recognize identifiers character by character, its grammar would be enormous and slow. Separating the lexer also gives one place to handle comments, line numbers, character sets, and input buffering, and it makes the parser grammar smaller and more readable.

2.2 Longest match, priority, and one character of lookahead

Lexers use the longest-match rule (also called maximal munch): among all patterns that match at the current position, take the longest lexeme. If two patterns match the same longest lexeme, the earlier rule in the lexer specification wins. This is why >= is not read as > followed by =, and why if is a keyword rather than an identifier.

Example. With rules “>= before >” and “keyword if before identifier,” the input if x >= 10 becomes <if> <id,x> <ge> <num,10>. The lexer had to look one character past > to see the =; if the next character had been a space, it would have stopped at >.

Most lexers need only one character of lookahead beyond the current lexeme, because regular languages can be recognized by a DFA that reads left to right. When the DFA has gone one character too far, the lexer backs up to the last accepting position. A common implementation keeps two buffers and places a sentinel character at the end of each, so the inner loop does not need a bounds check on every character. The sentinel is a real implementation trick, not a language feature; it must not be a character that can occur in the source, or the buffer logic must handle it.

Heads-up: reserved words versus identifiers. If the identifier pattern is letter (letter | digit)*, it also matches if, while, and return. A lexer generator handles this either by putting keyword rules first (so the earlier-rule tie-break wins) or by recognizing an identifier and then looking it up in a keyword table. Do not say “the identifier pattern excludes keywords” unless your pattern actually does; the usual pattern does not.

2.3 The language toolkit: strings, languages, and regular expressions

A string is a finite sequence of symbols from an alphabet \(\Sigma\). The empty string is \(\varepsilon\); it has length zero. If \(s\) and \(t\) are strings, \(st\) is their concatenation. The notation \(s^n\) means \(s\) repeated \(n\) times, with \(s^0=\varepsilon\). A language is a set of strings, so it is a subset of \(\Sigma^*\), the set of all strings over \(\Sigma\).

Three operations build languages:

  • Union: \(L \cup M = \{\,w \mid w\in L \text{ or } w\in M\,\}\).
  • Concatenation: \(LM = \{\,st \mid s\in L,\ t\in M\,\}\).
  • Kleene star: \(L^*\) is the union of \(L^0, L^1, L^2,\ldots\), where \(L^0=\{\varepsilon\}\). The positive closure \(L^+\) is \(LL^*\), i.e. one or more repetitions.

The empty language \(\varnothing\) and the language \(\{\varepsilon\}\) are different. \(\varnothing\) contains no strings; \(\{\varepsilon\}\) contains exactly the empty string. This distinction matters in regex identities: \(r\varnothing=\varnothing\), while \(r\varepsilon=r\).

A regular expression over \(\Sigma\) is defined inductively:

  • \(\varnothing\), \(\varepsilon\), and each \(a\in\Sigma\) are regular expressions.
  • If \(r\) and \(s\) are regular expressions, then \((r|s)\), \((rs)\), and \((r)^*\) are regular expressions.
  • Nothing else is a regular expression unless it can be built by these rules.

Precedence, from tightest to loosest, is star, then concatenation, then union. So \(ab^*|c\) means \((a(b^*))|c\), not \((ab)^*|c\) and not \(a(b^*|c)\). Parentheses override precedence. Many writers use \(r^+\) as shorthand for \(rr^*\), and \(r?\) for \(r|\varepsilon\).

Examples that are worth memorizing.
  • Identifiers: \(\texttt{letter}\,(\texttt{letter}\mid\texttt{digit})^*\), where letter is [A-Za-z_] and digit is [0-9].
  • Unsigned integers: \(\texttt{digit}^+\).
  • Optional sign: \((+|-)?\,\texttt{digit}^+\).
  • A simple floating literal: \(\texttt{digit}^+\.\texttt{digit}^*\) or \(\.\texttt{digit}^+\). In a real lexer, the dot must be escaped and the alternatives combined carefully.
  • Strings with backslash escapes: "([^"\\]|\\.)*". The negated class and the escape branch together say “any character except a quote or backslash, or a backslash followed by any character.”
  • All strings over \(\{a,b\}\) that end in abb: \((a|b)^*abb\).

Regular expressions obey algebraic laws that are useful for simplification and for seeing why two patterns describe the same language:

\[ \begin{aligned} r|s &= s|r, & (r|s)|t &= r|(s|t), \\ (rs)t &= r(st), & r(s|t) &= rs|rt, \\ \varepsilon r &= r, & \varnothing r &= \varnothing, \\ (r^*)^* &= r^*, & (r|\varepsilon)^* &= r^*, \\ r^+ &= rr^* = r^*r. \end{aligned} \]

These are language equalities, not just notation. For example, \((r^*)^*=r^*\) because any number of repetitions of any number of repetitions is still some number of repetitions.

Key. A token class is a language; a pattern is a regular expression; the lexer is a recognizer for the union of all token patterns, with longest-match and rule-order tie-breaking layered on top.
Heads-up: regular expressions cannot count nesting. A regular expression can say “any number of as,” but it cannot say “\(n\) opening parentheses followed by \(n\) closing parentheses” for arbitrary \(n\). That language needs a stack, so it belongs to the parser, not the lexer. This is the practical reason comments with nested delimiters, balanced brackets, and indentation-sensitive blocks are not handled by a pure regular-expression lexer.

2.4 Finite automata: the machine behind the pattern

A deterministic finite automaton (DFA) has a finite set of states \(Q\), an input alphabet \(\Sigma\), a transition function \(\delta:Q\times\Sigma\to Q\), a start state \(q_0\), and a set of accepting states \(F\). It reads one character at a time and moves to exactly one next state. It accepts a string if the state after the last character is in \(F\).

A nondeterministic finite automaton (NFA) relaxes two things: from a state and a character there may be zero, one, or many next states, and there may be \(\varepsilon\)-transitions that consume no input. Formally, \(\delta:Q\times(\Sigma\cup\{\varepsilon\})\to 2^Q\). An NFA accepts if some path through the machine ends in an accepting state. The NFA does not guess; “some path” is a mathematical statement about existence.

DFAs and NFAs accept exactly the same class of languages: the regular languages. The NFA is easier to build from a regular expression; the DFA is faster to execute because there is no choice and no \(\varepsilon\)-closure at run time. The standard route is therefore:

Thompson’s construction builds an NFA with one start state and one accepting state for each subexpression. The five shapes are worth drawing once and then recognizing forever.

2.6 Subset construction: NFA to DFA

The key operation is the \(\varepsilon\)-closure of a set of NFA states: all states reachable from that set using only \(\varepsilon\)-edges, including the states themselves. For a set \(T\) and a character \(a\), \(\text{move}(T,a)\) is the set of states reachable from a state in \(T\) by one \(a\)-edge. A DFA state is a set of NFA states. Starting from \(\varepsilon\text{-closure}(\{q_0\})\), repeatedly compute

\[ \text{next}(S,a)=\varepsilon\text{-closure}\bigl(\text{move}(S,a)\bigr) \]

for each symbol \(a\). Each distinct set becomes one DFA state. A DFA state is accepting if it contains any NFA accepting state. The construction is often done lazily: only create the sets that are actually reachable from the start.

The same example, subset by subset. Start with \(A=\varepsilon\text{-closure}(\{0\})=\{0,1,2,4,6,7\}\).
  • From \(A\) on \(a\): states 2 and 7 move to 3 and 8; closure adds 6, 1, 7, 2, 4, so \(B=\{1,2,3,4,6,7,8\}\).
  • From \(A\) on \(b\): state 4 moves to 5; closure adds 6, 1, 7, 2, 4, so \(C=\{1,2,4,5,6,7\}\).
  • From \(B\) on \(a\): states 2 and 7 move to 3 and 8; closure gives \(B\) again. On \(b\): 4 and 8 move to 5 and 9; closure gives \(E=\{1,2,4,5,6,7,9\}\).
  • From \(C\) on \(a\): 2 and 7 move to 3 and 8; closure gives \(B\). On \(b\): 4 moves to 5; closure gives \(C\).
  • From \(E\) on \(a\): 2 and 7 move to 3 and 8; closure gives \(B\). On \(b\): 4 and 9 move to 5 and 10; closure gives \(F=\{1,2,4,5,6,7,10\}\).
  • From \(F\) on \(a\): 2 and 7 move to 3 and 8; closure gives \(B\). On \(b\): 4 moves to 5; closure gives \(C\).
The reachable DFA states are \(A,B,C,E,F\). Only \(F\) is accepting, because it is the only subset that contains 10. Notice that \(A\) and \(C\) have exactly the same transitions: both go to \(B\) on \(a\) and to \(C\) on \(b\). They are equivalent and can be merged.

Heads-up: do not merge states just because both are non-accepting. \(A\) and \(B\) are both non-accepting, but \(B\) can reach the accepting state \(F\) after reading \(bb\), while \(A\) cannot. 2.7 DFA minimization: keep only distinguishable states

Two states are equivalent if, for every input string, starting from either one leads to acceptance exactly when starting from the other does. Minimization starts with two blocks, accepting and non-accepting, and repeatedly splits a block whenever two of its states go to different blocks on some symbol. When no block can be split, each block is one state of the minimal DFA.

On the table above. Initial blocks: \(\{A,B,C,E\}\) and \(\{F\}\). On \(b\), \(E\) goes to \(F\) (the accepting block) while \(A,B,C\) go to non-accepting states, so split \(E\) out. Now consider \(\{A,B,C\}\): on \(a\) all go to \(B\), but on \(b\), \(A\) and \(C\) go to \(C\) while \(B\) goes to \(E\) (now a separate block), so split \(B\) out. Final blocks: \(\{A,C\}\), \(\{B\}\), \(\{E\}\), \(\{F\}\). That is the four-state DFA.

The minimal DFA for a regular language is unique up to renaming states. That is why two different lexer generators can produce different-looking tables for the same token patterns and still behave identically.

2.8 How a real lexer uses all this

A lexer generator such as Lex or Flex takes regular definitions and rules, builds one NFA for all token patterns (or one per pattern and combines them), converts to a DFA, minimizes it, and emits a table-driven matcher. Each accepting DFA state is annotated with the rule that matched and the action to run. The driver repeatedly finds the longest accepting prefix, executes that action, and moves the input pointer to the end of the lexeme.

%{
#include "tokens.h"
%}
digit   [0-9]
letter  [A-Za-z_]
%%
"if"            { return IF; }
{letter}({letter}|{digit})*  { yylval.s = strdup(yytext); return ID; }
{digit}+        { yylval.n = atoi(yytext); return NUM; }
">="           { return GE; }
">"            { return GT; }
[ \t\n]+        { /* skip layout */ }
.               { error("illegal character"); }

The declarations section defines named regular expressions; the rules section lists pattern–action pairs; the user-code section is copied into the generated program. yytext points at the matched lexeme and yyleng is its length. Longest match is the default; if two rules match the same length, the earlier rule wins. A rule can call yyless(n) to push back part of the match, or REJECT to try the next-best rule (rare and slower). Start conditions let one lexer handle modes such as “inside a string” or “inside a comment.”

The generated matcher is essentially a DFA plus a stack of the last accepting position. When it reaches a dead state or the end of the buffer, it backs up to the last accepting position. If there is no accepting position, the lexer reports a lexical error and applies a recovery rule: skip one character, skip to the next delimiter, insert a missing quote, or abort the current line.

Key. Regex → NFA is construction; NFA → DFA is subset construction (closure + move); DFA → minimal DFA is partition refinement. The lexer runs the minimal DFA, remembers the longest accepting prefix, and executes the winning rule.
Heads-up: subset construction can explode. An \(n\)-state NFA can produce up to \(2^n\) DFA states. In practice, lexer patterns are simple and the reachable subset is small; generators build it lazily and minimize it. If an exam asks for the maximum, the answer is \(2^n\), not \(n^2\).
Heads-up: lexical errors are not syntax errors. An illegal character or an unterminated string is lexical: no token can be formed. A missing semicolon or an unmatched parenthesis is syntactic: the tokens are fine, but their arrangement is not. A type mismatch is semantic. The phase that detects the error is part of the answer.

3. Grammars, derivations, and ambiguity

A lexer recognizes words. A parser recognizes sentences. The tool for describing sentences is a context-free grammar (CFG). It is called context-free because a nonterminal can be replaced by any of its productions no matter what surrounds it. That is exactly the right amount of power for nested expressions, statements, and blocks, and it is not enough power to enforce “this variable was declared” or “these types match” — those checks belong to semantic analysis.

3.1 The four parts of a grammar

A CFG is a tuple \(G=(V,T,P,S)\):

  • \(V\) is a finite set of nonterminals (also called variables). They are the syntactic categories: expression, statement, declaration.
  • \(T\) is a finite set of terminals (the tokens). \(V\cap T=\varnothing\).
  • \(P\) is a finite set of productions, each of the form \(A\to\alpha\), where \(A\in V\) and \(\alpha\in(V\cup T)^*\).
  • \(S\in V\) is the start symbol.

By convention, uppercase letters near the start of the alphabet are nonterminals, lowercase letters near the end are terminals, \(S\) is the start symbol, and Greek letters stand for strings of grammar symbols. A production with the same left side can be written with alternatives: \(A\to\alpha\mid\beta\) means two productions, \(A\to\alpha\) and \(A\to\beta\).

A grammar for arithmetic expressions with precedence and associativity. 
E → E + T | T
T → T * F | F
F → ( E ) | id
Here E is an expression, T a term, and F a factor. The grammar says: an expression is a sum of terms; a term is a product of factors; a factor is a parenthesized expression or an identifier. The layering is what makes * bind tighter than +. The left-recursive shape \(E\to E+T\) is what makes + left-associative.

3.2 Derivations: a proof that a string belongs

A derivation starts with \(S\) and repeatedly replaces a nonterminal by the right side of one of its productions. Write \(\Rightarrow\) for one step and \(\Rightarrow^*\) for zero or more steps. A string of grammar symbols that appears during a derivation is a sentential form; if it contains only terminals, it is a sentence. The language of the grammar, \(L(G)\), is the set of terminal strings derivable from \(S\).

A leftmost derivation always replaces the leftmost nonterminal. A rightmost derivation always replaces the rightmost nonterminal. Both are canonical ways to record the same parse tree; the tree does not care which nonterminal you chose first.

Leftmost derivation of id + id * id. 
E ⇒ E + T
  ⇒ T + T
  ⇒ F + T
  ⇒ id + T
  ⇒ id + T * F
  ⇒ id + F * F
  ⇒ id + id * F
  ⇒ id + id * id
The corresponding parse tree: 
            E
          / | \
         E  +  T
         |    /|\
         T   T * F
         |   |   |
         F   F  id
         |   |
        id  id
The yield of the tree, read left to right, is id + id * id. The tree groups the multiplication under the right operand of +, so the meaning is id + (id * id). The grammar encoded the precedence; no separate rule was needed.

The same string has a rightmost derivation, obtained by always expanding the rightmost nonterminal:

\[ E\Rightarrow E+T\Rightarrow E+T*F\Rightarrow E+T*id\Rightarrow E+F*id\Rightarrow E+id*id\Rightarrow T+id*id\Rightarrow F+id*id\Rightarrow id+id*id \]

Different derivation order, same tree. When people say “the parse tree” they mean the structural grouping; when they say “a derivation” they mean one particular order of expanding it.

3.3 Ambiguity: one string, two trees

A grammar is ambiguous if some terminal string has more than one parse tree (equivalently, more than one leftmost derivation, or more than one rightmost derivation). Ambiguity is a property of the grammar, not necessarily of the language: a language may have an unambiguous grammar and also an ambiguous one. A language is inherently ambiguous if every grammar for it is ambiguous.

The classic ambiguous expression grammar. 
E → E + E | E * E | ( E ) | id
For id + id * id, there are two trees. The first groups the addition first: 
          E                 E
        / | \             / | \
       E  *  E           E  +  E
     /|\     |           |    /|\
    E + E   id          id   E * E
    |   |                    |   |
   id  id                   id  id
The left tree means \((id+id)*id\); the right tree means \(id+(id*id)\). Both yields are the same terminal string, so the grammar does not tell the parser which meaning to choose. The earlier layered grammar \(E\to E+T\mid T\), \(T\to T*F\mid F\), \(F\to(E)\mid id\) has only the right-hand grouping.

Ambiguity is not always about arithmetic. The dangling else is the standard statement-level example:

stmt → if expr then stmt
     | if expr then stmt else stmt
     | other

For

if E1 then if E2 then S1 else S2

the else can pair with the inner if E2 or with the outer if E1. Both parse trees are legal. Most languages choose the nearest unmatched then, so the else belongs to the inner if. A grammar can enforce that choice by separating matched statements (which have their own else) from unmatched ones:

stmt     → matched | unmatched
matched  → if expr then matched else matched
         | other
unmatched → if expr then stmt
          | if expr then matched else unmatched

In this grammar, an if without an else is unmatched, and an else can only close a matched if. The outer if E1 in the example is unmatched, and the inner one is matched. No ambiguity remains.

Why ambiguity is a parsing problem, not just a style problem. A parser must choose a production at each step. If two parse trees exist, the grammar gives it no deterministic choice. A parser generator may report a conflict, pick one alternative by rule order, or parse the wrong meaning silently. In a compiler, the parse tree drives code generation; two trees can produce different answers. That is why language designers either write an unambiguous grammar or add disambiguating rules (precedence, associativity, “else matches nearest if”) and prove those rules match the intended language.

3.4 Context-free versus regular

Every regular language is context-free, but not every context-free language is regular. The standard witness is

\[ L=\{\,a^n b^n \mid n\ge 0\,\} \]

A grammar for it is \(S\to aSb\mid\varepsilon\). A finite automaton cannot recognize it because it would need to remember an unbounded count of \(a\)s. A pushdown automaton can, because it has a stack; a CFG is the declarative counterpart of a pushdown automaton. This is the formal reason nested constructs — parentheses, blocks, nested function calls — need a parser and cannot be handled by a lexer alone.

Nesting in a real grammar. The production \(F\to(E)\) is recursive: an expression can contain an expression in parentheses, which can contain another, and so on. The recursion is what gives the grammar unbounded nesting. A regular expression can match a fixed number of parentheses or a flat sequence, but not “any number of opens followed by the same number of closes.”

3.5 Grammar transformations you will use later

Parsers often need a grammar in a different shape. These transformations preserve the language, but they may change the parse trees, so they must be used carefully when semantic actions depend on tree shape.

  • Eliminate left recursion. A production \(A\to A\alpha\mid\beta\) becomes \(A\to\beta A'\) and \(A'\to\alpha A'\mid\varepsilon\). This removes immediate left recursion; indirect left recursion needs a general algorithm. Top-down parsers need this because a recursive-descent procedure for \(A\) would call itself before consuming a token.
  • Left-factor. \(A\to\alpha\beta_1\mid\alpha\beta_2\) becomes \(A\to\alpha A'\) and \(A'\to\beta_1\mid\beta_2\). This delays the choice until the parser has seen enough input to distinguish the alternatives.
  • Eliminate useless symbols. Remove nonterminals that cannot derive a terminal string (non-generating) and symbols that cannot be reached from the start (unreachable). They add nothing to the language.
  • Eliminate \(\varepsilon\)-productions and unit productions. Useful for normal forms and some algorithms. Removing \(\varepsilon\)-productions can increase the number of productions; removing \(A\to B\) means substituting \(B\)’s productions into \(A\).
  • Chomsky normal form. Every production is \(A\to BC\) or \(A\to a\) (plus possibly \(S\to\varepsilon\)). It is a theoretical normal form, not usually what a hand-written parser uses.
Key. A grammar generates strings by derivation; a parse tree records the grouping; a leftmost or rightmost derivation is just a canonical order. Ambiguity means two trees for one string. Precedence, associativity, and “nearest else” are disambiguation rules, and a grammar can often encode them directly.
Heads-up: “the grammar is ambiguous” and “the language is ambiguous” are different claims. The ambiguous expression grammar above generates the same language as the layered grammar; the language is not inherently ambiguous. Also, a grammar can be unambiguous but still not LL(1) or not LR(1); parsing power is a separate question from ambiguity.

4. Top-down parsing: predict the next move

A top-down parser starts at the start symbol and tries to derive the input. At each step it looks at the next input token and chooses a production for the leftmost nonterminal. If the grammar is designed well, one token is enough to choose. That is the whole idea of predictive parsing.

4.1 Recursive descent: one function per nonterminal

The most direct implementation is recursive descent. Each nonterminal becomes a function. The function consumes tokens that match its production and calls the functions for the nonterminals on the right side. A global variable holds the current lookahead token.

Left recursion makes this scheme loop forever: a function for \(A\to A\alpha\) would call itself before consuming anything. So the first step is to rewrite the grammar without left recursion. For the expression grammar, one useful form is:

E  → T E'
E' → + T E' | ε
T  → F T'
T' → * F T' | ε
F  → ( E ) | id

Now the recursive-descent skeleton is almost a transcription:

void E()  { T(); Eprime(); }
void Eprime() {
    if (look == '+') { match('+'); T(); Eprime(); }
    else if (look == ')' || look == '$') return;   // ε-production
    else error();
}
void T()  { F(); Tprime(); }
void Tprime() {
    if (look == '*') { match('*'); F(); Tprime(); }
    else if (look == '+' || look == ')' || look == '$') return;
    else error();
}
void F() {
    if (look == 'id') match('id');
    else if (look == '(') { match('('); E(); match(')'); }
    else error();
}

The else if branches are the \(\varepsilon\)-productions. The parser takes an \(\varepsilon\)-production when the lookahead cannot begin the recursive alternative but can legally follow the nonterminal. That “can legally follow” set is FOLLOW. The set that can begin a string is FIRST. Those two sets are the entire decision procedure.

Why one token can be enough. At a nonterminal \(A\), the parser has already matched the input to the left of \(A\). The next token must be the first token of whatever \(A\) derives. If each alternative of \(A\) begins with a distinct set of tokens, the lookahead picks the alternative. If an alternative can derive \(\varepsilon\), the parser may also choose it when the next token is something that can follow \(A\). That is the LL(1) condition, stated in advance.

4.2 FIRST: what can a string begin with?

For a string \(\alpha\) of grammar symbols, \(\text{FIRST}(\alpha)\) is the set of terminals that can appear as the first symbol of some string derived from \(\alpha\). If \(\alpha\Rightarrow^*\varepsilon\), then \(\varepsilon\in\text{FIRST}(\alpha)\).

The computation is a fixed point over the productions:

  • \(\text{FIRST}(\varepsilon)=\{\varepsilon\}\).
  • For a terminal \(a\), \(\text{FIRST}(a)=\{a\}\).
  • For a nonterminal \(A\), add \(\text{FIRST}(\alpha)\) for every production \(A\to\alpha\). If every alternative can derive \(\varepsilon\), add \(\varepsilon\) to \(\text{FIRST}(A)\).
  • For a string \(X_1X_2\cdots X_n\), add \(\text{FIRST}(X_1)\). If \(X_1\) is nullable, also add \(\text{FIRST}(X_2)\); if both are nullable, continue. If every \(X_i\) is nullable, add \(\varepsilon\).

“Nullable” means “can derive \(\varepsilon\).” A nonterminal is nullable if it has a production whose right side is entirely nullable (or is \(\varepsilon\)). This is another fixed point: start with the nonterminals that have \(\varepsilon\)-productions, then propagate through productions whose right sides are all nullable.

FIRST for the expression grammar. 
FIRST(F)  = { (, id }
FIRST(T)  = { (, id }
FIRST(E)  = { (, id }
FIRST(E') = { +, ε }
FIRST(T') = { *, ε }
Why: \(F\to(E)\mid id\), so its first tokens are ( and id. \(T\to F T'\), and \(F\) is not nullable, so \(T\) begins exactly like \(F\). The same argument gives \(E\). \(E'\) has alternatives \(+TE'\) and \(\varepsilon\), so its FIRST is \(\{+\}\cup\{\varepsilon\}\). \(T'\) is analogous with \(*\).

4.3 FOLLOW: what can come after a nonterminal?

\(\text{FOLLOW}(A)\) is the set of terminals that can appear immediately to the right of \(A\) in some sentential form derived from the start symbol. If \(A\) can be at the end of the input, the end marker \(\$\) is in \(\text{FOLLOW}(A)\). FOLLOW never contains \(\varepsilon\); it contains terminals and \(\$\).

The rules:

  • Put \(\$\) in \(\text{FOLLOW}(S)\) for the start symbol \(S\).
  • For every production \(A\to\alpha B\beta\), put \(\text{FIRST}(\beta)-\{\varepsilon\}\) into \(\text{FOLLOW}(B)\).
  • For every production \(A\to\alpha B\beta\) where \(\beta\Rightarrow^*\varepsilon\), put \(\text{FOLLOW}(A)\) into \(\text{FOLLOW}(B)\). The same applies to \(A\to\alpha B\) (take \(\beta=\varepsilon\)).

Read the second rule as: “\(B\) is followed by whatever can begin \(\beta\).” Read the third as: “if \(\beta\) can vanish, \(B\) is followed by whatever follows \(A\).” Iterate until no set changes.

FOLLOW for the expression grammar. 
FOLLOW(E)  = { ), $ }
FOLLOW(E') = { ), $ }
FOLLOW(T)  = { +, ), $ }
FOLLOW(T') = { +, ), $ }
FOLLOW(F)  = { *, +, ), $ }
Derivation of the less obvious ones:
  • \(E\) is the start, so \(\$\) is in FOLLOW(E). The production \(F\to(E)\) puts \()\) after \(E\).
  • \(E'\) appears at the end of \(E\to T E'\), so FOLLOW(E) flows into FOLLOW(E'). The production \(E'\to+TE'\) has \(E'\) at the end again; no new terminals.
  • \(T\) appears in \(E\to T E'\). It is followed by \(E'\), whose FIRST is \(\{+,\varepsilon\}\); add \(+\). Since \(E'\) is nullable, also add FOLLOW(E) \(=\{), \$\}\).
  • \(T'\) appears at the end of \(T\to F T'\), so FOLLOW(T) flows into FOLLOW(T'). The production \(T'\to*FT'\) keeps \(T'\) at the end; no new terminals.
  • \(F\) appears in \(T\to F T'\). It is followed by \(T'\), whose FIRST is \(\{*,\varepsilon\}\); add \(*\). Since \(T'\) is nullable, add FOLLOW(T) \(=\{+,), \$\}\).
Key. FIRST answers “what can this string start with?” and may contain \(\varepsilon\). FOLLOW answers “what can come after this nonterminal?” and never contains \(\varepsilon\). A nullable nonterminal needs FOLLOW to decide when to take its \(\varepsilon\)-production.
Heads-up: FOLLOW is not “the set of all tokens that ever appear after A in the grammar text.” It is computed from the start symbol and propagates through nullable suffixes. A token that appears after \(A\) in one production may not be in FOLLOW(A) if that context is unreachable, and a token can be in FOLLOW(A) because of a chain of nullable symbols. Use the rules, not intuition.

4.4 The LL(1) table: turn decisions into a lookup

An LL(1) parser can be implemented as a table \(M[A,a]\), where \(A\) is a nonterminal and \(a\) is the current lookahead token. The entry is the production to use, or an error. The table is built directly from FIRST and FOLLOW:

  • For each production \(A\to\alpha\) and each terminal \(a\in\text{FIRST}(\alpha)\), put \(A\to\alpha\) in \(M[A,a]\).
  • If \(\varepsilon\in\text{FIRST}(\alpha)\), then for each \(b\in\text{FOLLOW}(A)\), put \(A\to\alpha\) in \(M[A,b]\).

If any cell receives two different productions, the grammar is not LL(1). That is the table form of the LL(1) condition: alternatives must have disjoint FIRST sets, and any nullable alternative must not overlap with FOLLOW.

The LL(1) table for the expression grammar. Blank cells are errors.
id()+*$

Check one entry: \(E'\to\varepsilon\) appears under \()\) and \(\$\) because FOLLOW(E′) \(=\{), \$\}\). It does not appear under \(+\), because \(+\) is in FIRST(+T E′), so the recursive production wins there. It does not appear under \(*\) or \(id\), because those cannot follow \(E'\) in this grammar.

4.5 A full LL(1) parse, stack and all

The table-driven parser keeps a stack whose bottom is \(\$\) and whose top is the next symbol to expand or match. Initially the stack is \(\$E\). The input ends with \(\$\). At each step:

  • If the top is a terminal and matches the lookahead, pop it and advance the input.
  • If the top is a nonterminal \(A\), look up \(M[A,\text{lookahead}]\) and replace \(A\) by the right side of that production, reversed so the leftmost symbol is on top.
  • If the top is \(\$\) and the lookahead is \(\$\), accept.
  • Otherwise, report a syntax error.

4.6 Left recursion: why it breaks top-down, and how to remove it

A production \(A\to A\alpha\) is immediately left-recursive. A recursive-descent parser for \(A\) would call \(A\) again before consuming a token, so it would recurse forever. Indirect left recursion, such as \(A\to B\alpha\), \(B\to A\beta\), has the same effect through a cycle.

The immediate case has a mechanical rewrite:

\[ A\to A\alpha\mid\beta \quad\Longrightarrow\quad A\to\beta A',\qquad A'\to\alpha A'\mid\varepsilon \]

Here \(\beta\) is any alternative that does not begin with \(A\). The new nonterminal \(A'\) consumes zero or more repetitions of \(\alpha\). For the expression grammar:

\[ E\to E+T\mid T \quad\Longrightarrow\quad E\to T E',\qquad E'\to+T E'\mid\varepsilon \]

The same rewrite on \(T\to T*F\mid F\) gives \(T\to F T'\), \(T'\to*F T'\mid\varepsilon\). This is exactly the grammar used in the recursive-descent code above.

For indirect left recursion, order the nonterminals \(A_1,\ldots,A_n\) and eliminate in that order. For each \(A_i\), first replace any production \(A_i\to A_j\gamma\) with \(j<i\) by substituting all current \(A_j\)-productions, then eliminate immediate left recursion for \(A_i\). After the loop, no production begins with a nonterminal that can eventually lead back to its left side. The algorithm assumes there are no cycles \(A\Rightarrow^+A\) and no \(\varepsilon\)-productions that create them; remove those first if necessary.

Heads-up: removing left recursion changes the parse tree, not just the notation. The original \(E\to E+T\) builds a left-leaning tree that naturally means \((a+b)+c\). The rewritten grammar builds a right-leaning tree with an \(E'\) tail. If your semantic actions assume the original shape, you must adapt them (for example, pass an accumulated value through an inherited attribute). The language is the same; the tree is not.

4.7 Left factoring: delay the choice until you can make it

Two alternatives with a common prefix make the FIRST sets overlap. The parser sees the prefix and cannot tell which alternative to choose. Left factoring pulls the common prefix out:

\[ A\to\alpha\beta_1\mid\alpha\beta_2 \quad\Longrightarrow\quad A\to\alpha A',\qquad A'\to\beta_1\mid\beta_2 \]

For example, if a statement can be an assignment or a call, both beginning with an identifier:

stmt → id = expr ;
     | id ( args ) ;

factor to

stmt  → id stmt'
stmt' → = expr ;
      | ( args ) ;

The parser consumes id first, then decides from the next token. With more than two alternatives, factor the longest common prefixes repeatedly. Left factoring is necessary for LL(1) in many grammars, but it is not sufficient by itself: the resulting grammar can still have FIRST/FOLLOW overlaps, and it can still be ambiguous. The dangling-else grammar, for instance, has a common prefix but needs a disambiguation rule, not just factoring.

4.8 Errors in top-down parsing

When the table entry is blank or a terminal does not match, the parser has a syntax error. A simple recovery is panic mode: pop the stack until the top is a nonterminal whose FOLLOW set contains the lookahead, or until the lookahead is a token that can restart the parse (a semicolon, a closing brace, or end of file). Then skip input tokens until one is in that sync set. This lets the parser report several errors instead of stopping at the first one.

A more precise approach is phrase-level recovery: add explicit error productions for common mistakes, such as a missing semicolon or a missing closing parenthesis. The parser then has a legal action for the erroneous input and can continue. Parser generators often support an error token for this purpose.

Key. LL(1) means left-to-right scan, leftmost derivation, one lookahead token. Build FIRST and FOLLOW, fill the table, and parse with a stack. Left recursion must be removed; common prefixes should be factored; nullable alternatives are chosen on FOLLOW.
Heads-up: “no left recursion and no common prefixes” does not guarantee LL(1). Two alternatives can have disjoint FIRST sets and still conflict through FOLLOW if one is nullable, and a grammar can have hidden overlaps after several symbols. The table is the test: one production per cell, or it is not LL(1).
Heads-up: left recursion is not “bad grammar.” It is bad for top-down parsing and fine for bottom-up parsing. LR parsers handle \(E\to E+T\) directly and often more naturally than the transformed grammar. The right question is “which parser?” not “which grammar is universally correct?”

5. Bottom-up parsing: shift, reduce, and LR

A bottom-up parser starts with the input tokens and reduces them back to the start symbol. It reads left to right, and the sequence of reductions is a rightmost derivation in reverse. The family of parsers that do this with a stack and a deterministic table is the LR family. LR parsers are the industrial default because they handle left recursion, a large class of grammars, and precise lookahead without backtracking.

5.1 Shift-reduce parsing: the stack story

A shift-reduce parser has a stack and an input stream. It performs four kinds of actions:

  • Shift: move the next input token onto the stack.
  • Reduce: replace the right side of a production on top of the stack by its left side. For example, if the stack ends in id and the grammar has \(T\to id\), replace id by \(T\).
  • Accept: the stack contains the start symbol and the input is exhausted.
  • Error: no legal action.

The string on top of the stack that matches a production’s right side is a handle. The stack always holds a viable prefix: a prefix of a right sentential form that can still be extended to a complete reduction. The parser’s job is to find the handle and reduce it at the right time.

A tiny trace. Grammar: \(E\to E+T\mid T\), \(T\to id\). Input: id + id.

Two questions remain: how does the parser know when to shift versus reduce, and which production to reduce? The LR construction answers both by building a finite automaton whose states summarize “how much of which productions we have seen.”

5.2 LR(0) items: a production with a dot

An LR(0) item is a production with a dot somewhere on the right side. The dot marks how much of the right side has already been recognized. For \(E\to E+T\), the four items are

\[ E\to \cdot E+T,\qquad E\to E\cdot+T,\qquad E\to E+\cdot T,\qquad E\to E+T\cdot \]

The first says “we are about to look for an \(E\), then \(+\), then \(T\).” The last says “we have recognized the whole right side; we may reduce.” The dot can also be at the end of an \(\varepsilon\)-production: \(A\to\cdot\) means “the empty right side is already recognized.”

The closure of a set of items adds items for nonterminals that appear immediately after a dot. If \(A\to\alpha\cdot B\beta\) is in the set, then every production \(B\to\gamma\) contributes \(B\to\cdot\gamma\). Repeat until no new items. Intuitively, if the parser is about to look for a \(B\), it must be prepared to start any production for \(B\).

The goto function moves the dot over a grammar symbol \(X\): from all items \(A\to\alpha\cdot X\beta\), form \(A\to\alpha X\cdot\beta\), then take the closure. The canonical collection of LR(0) item sets is built by starting from the closure of the augmented start item \(S'\to\cdot S\) and repeatedly applying goto for every grammar symbol.

5.3 SLR tables: use FOLLOW to decide reductions

A state containing a completed item \(A\to\alpha\cdot\) is a candidate for reduction. In the simplest LR(0) table, it would reduce on every lookahead, which causes many conflicts. Simple LR (SLR) restricts the reduction to the lookaheads in \(\text{FOLLOW}(A)\). The table has two parts:

  • ACTION[state, terminal]: shift to a state, reduce by a production, accept, or error.
  • GOTO[state, nonterminal]: the state to enter after a reduction exposes that nonterminal.

At a reduction by \(A\to\beta\), the parser pops \(2|\beta|\) symbols (grammar symbols and states), then uses the exposed state and \(A\) in GOTO to find the next state. Here, reducing \(T\to id\) pops id 3, exposes state 0, and GOTO(0,T)=2. Reducing \(E\to E+T\) pops E 1 + 4 T 5, exposes state 0, and GOTO(0,E)=1.
Key. LR parsing is left-to-right scanning with a rightmost derivation in reverse. The stack is a viable prefix; the table decides shift, reduce, accept, or error. SLR uses FOLLOW as the reduce lookahead.
Heads-up: “reduce” does not mean “replace the first matching symbols anywhere.” It means replace the handle on top of the stack. The stack must end with the production’s right side. If it does not, the parser is in the wrong state, even if the same symbols appear earlier.

5.4 Why SLR is not the end: lookahead can be too coarse

SLR reduces \(A\to\alpha\) whenever the lookahead is anywhere in \(\text{FOLLOW}(A)\). FOLLOW is a global set: it says a token can follow \(A\) somewhere, not that it can follow \(A\) in this particular state. That over-approximation can create a conflict in a grammar that is perfectly unambiguous.

The classic SLR conflict. Grammar: 
S → L = R | R
L → * R | id
R → L
After seeing an \(L\), the LR(0) state contains both \(S\to L\cdot=R\) and \(R\to L\cdot\). The first item wants to shift \(=\). The second wants to reduce \(R\to L\). Since \(\text{FOLLOW}(L)=\{=,\$\}\), SLR allows the reduction on \(=\), so the state has a shift/reduce conflict on \(=\). The language is not ambiguous: after an \(L\) that came from the start symbol, \(=\) must continue an assignment; after an \(L\) that came from \(*R\), \(=\) may follow the inner \(R\). SLR cannot see that difference.

5.5 Canonical LR(1): carry the exact lookahead

An LR(1) item is a pair \([A\to\alpha\cdot\beta,\ a]\), where \(a\) is a terminal or the end marker \(\$\). The dot says how much has been recognized; the lookahead says which token is allowed to follow this occurrence of \(A\) when the item is completed. The closure rule is:

\[ \text{if }[A\to\alpha\cdot B\beta,\ a]\in I,\ \text{then for every }B\to\gamma\text{ and every }b\in\text{FIRST}(\beta a),\ \text{add }[B\to\cdot\gamma,\ b]. \]

The only change from LR(0) is the lookahead: the new item’s lookahead is a terminal that can begin \(\beta a\). Goto carries the lookaheads along. A completed item \([A\to\alpha\cdot,\ a]\) reduces only when the actual lookahead is \(a\).

For the assignment grammar, the state after \(L\) contains \([S\to L\cdot=R,\ \$]\) and \([R\to L\cdot,\ \$]\). The reduction is allowed only on \(\$\), not on \(=\). The shift on \(=\) is therefore unambiguous. The conflict is gone.

The price is size. Canonical LR(1) can have many more states than SLR, because the same LR(0) core can appear with different lookahead sets. A large programming-language grammar can produce thousands of states.

5.6 LALR: merge states with the same core

LALR(1) (“lookahead LR”) takes the canonical LR(1) automaton and merges any two states that have the same LR(0) core — the same items with the dots, ignoring lookaheads. The merged state’s lookahead for an item is the union of the lookaheads from the merged states. The result is usually close to SLR in size and close to LR(1) in power.

Merging can create a reduce/reduce conflict: two different productions may become reducible on the same lookahead after their lookahead sets are unioned. It cannot create a brand-new shift/reduce conflict, because the shift actions are determined by the core and are identical in states with the same core. If a shift/reduce conflict appears after merging, it was already present in one of the original states.

An LR(1) grammar that is not LALR(1). 
S → a A d | b A e | a B e | b B d
A → c
B → c
After a c, the parser needs to choose \(A\to c\) if the next token is \(d\), and \(B\to c\) if the next token is \(e\). After b c, the choices reverse. Canonical LR(1) keeps separate states for the two contexts. LALR merges the two \(c\)-states because their cores are the same \(\{A\to c\cdot,\ B\to c\cdot\}\), and the union of lookaheads makes both reductions legal on both \(d\) and \(e\). That is a reduce/reduce conflict. The grammar is LR(1), but not LALR(1).

5.8 Conflicts, and how to resolve them honestly

A conflict is a cell where the table wants two different actions. There are two kinds:

  • Shift/reduce: the state can shift the lookahead or reduce a completed production on that lookahead. Common causes: an ambiguous grammar (dangling else, unlayered expressions) or a grammar that is not LR.
  • Reduce/reduce: two completed productions can reduce on the same lookahead. Common causes: an ambiguous grammar, inadequate lookahead, or LALR merging.

There are three honest ways to handle a conflict:

  1. Rewrite the grammar so the choice is encoded structurally. This is the cleanest and the most portable. The matched/unmatched grammar for dangling else is an example.
  2. Add precedence and associativity declarations. This tells the parser how to choose in a shift/reduce conflict without rewriting the grammar. It is standard in Yacc/Bison.
  3. Use the parser generator’s default. Yacc/Bison shift by default on shift/reduce, and choose the earlier rule on reduce/reduce. This is sometimes acceptable, but it is a decision you must understand and document; a silent default can hide a real ambiguity.
Precedence and associativity on the ambiguous expression grammar. Grammar: \(E\to E+E\mid E*E\mid id\). Declare + and - left-associative and lower, * and / left-associative and higher. In a state with a completed \(E\to E+E\cdot\):
  • Lookahead \(*\): \(*\) has higher precedence than the production’s operator \(+\), so shift. This makes \(*\) bind tighter.
  • Lookahead \(+\): equal precedence, left-associative, so reduce. This makes \(+\) left-associative.
  • Lookahead \(\$\): reduce, because there is no operator to shift.
In a state with \(E\to E*E\cdot\), lookahead \(+\) has lower precedence, so reduce; lookahead \(*\) has equal precedence and left associativity, so reduce. A right-associative operator such as exponentiation would shift on equal precedence instead.

In Yacc/Bison, precedence declarations are listed from lowest to highest: %left '+' '-', then %left '*' '/', then %right '^'. A production’s precedence is the precedence of its rightmost terminal, unless %prec overrides it. On a shift/reduce conflict, compare the lookahead token’s precedence with the production’s precedence: higher token precedence means shift; lower means reduce; equal means use associativity (left: reduce, right: shift, nonassociative: error).

5.9 The dangling else in an LR parser

The grammar

stmt → if expr then stmt
     | if expr then stmt else stmt
     | other

has a shift/reduce conflict on else: after if expr then stmt, the parser can shift else (attach it to this if) or reduce the inner stmt (attach it to an outer if). The default shift resolves it to the nearest unmatched if, which is what most languages want. If the language wanted the other rule, the default would be wrong. The structural fix is the matched/unmatched grammar from Section 3; it removes the conflict instead of hiding it.

Key. LR(0) items track the dot; SLR reduces on FOLLOW; canonical LR(1) attaches an exact lookahead to each item; LALR merges same-core LR(1) states. Power: LR(0) ⊂ SLR ⊂ LALR ⊂ LR(1). Resolve conflicts by rewriting, by precedence, or by a deliberate default — never by pretending the conflict is not there.
Heads-up: a conflict-free table is not proof that the grammar matches the language you intended. A parser generator can resolve a conflict silently and produce a parser for a different language than you had in mind. Check the parse of the tricky sentence (the dangling else, the unary minus, the exponent’s associativity), not just the absence of warnings.
Heads-up: LALR is not “LR(1) with fewer states and no downside.” The merging can turn a pair of precise LR(1) states into a reduce/reduce conflict. If that happens, use canonical LR(1), rewrite the grammar, or use a tool that supports IELR/other refinements. The trade-off is real.

6. Syntax-directed translation: attach meaning to the tree

Parsing tells you the shape of the program. Syntax-directed translation tells you what the shape means. The idea is simple: give each grammar symbol some attributes (a value, a type, a place in the symbol table, a piece of generated code), and attach semantic rules to productions saying how to compute the attributes of the left side from the attributes of the right side. Walk the parse tree, evaluate the rules, and the meaning falls out.

6.1 Attributes, semantic rules, and annotated trees

A syntax-directed definition (SDD) is a context-free grammar plus, for each production, a set of semantic rules. Each rule defines an attribute of a grammar symbol in that production. The attributes of a node in the parse tree are written next to the node; the result is an annotated parse tree.

A desk calculator. 
E → E1 + T    { E.val = E1.val + T.val }
E → T         { E.val = T.val }
T → T1 * F    { T.val = T1.val * F.val }
T → F         { T.val = F.val }
F → ( E )     { F.val = E.val }
F → digit     { F.val = digit.lexval }
For 3 * 5 + 4, the annotated tree evaluates bottom-up: 
E.val = 19
├── E.val = 15
│   └── T.val = 15
│       ├── T.val = 3
│       │   └── F.val = 3
│       │       └── digit 3
│       ├── *
│       └── F.val = 5
│           └── digit 5
├── +
└── T.val = 4
    └── F.val = 4
        └── digit 4
The multiplication happens first because the \(T\) subtree is below the \(E\) subtree; the addition combines 15 and 4. The tree shape encoded precedence, and the semantic rules only did arithmetic.

The attribute val here is synthesized: its value at a node is computed from the values of the node’s children. Synthesized attributes flow upward. An inherited attribute flows downward or sideways: its value at a node is computed from the parent or from siblings. Inherited attributes are how a tree passes context down, such as “the declared type of this list is float” or “the type expected here is int.”

6.2 Inherited attributes: passing context down

A classic example is a declaration such as float x, y. The type is written once on the left, but every identifier in the list needs it. The type flows down the list through an inherited attribute.

D → T L          { L.in = T.type }
T → int          { T.type = int }
T → float        { T.type = float }
L → L1 , id      { L1.in = L.in;
                   addtype(id.entry, L.in) }
L → id           { addtype(id.entry, L.in) }

For float x, y, the root \(D\) gives \(L\) the inherited value float. The list node passes the same value to its left sibling \(L_1\), and each identifier is entered into the symbol table with that type. The parse tree is the same as before; the annotations are what changed.

How to tell synthesized from inherited. Ask: “Whose information does this attribute need?” If it needs only the children, it is synthesized. If it needs the parent or a sibling, it is inherited. In a production \(A\to X_1\cdots X_n\), a synthesized attribute of \(A\) is defined by a rule on \(A\); an inherited attribute of \(X_i\) is defined by a rule on \(X_i\) using attributes of \(A\) or of \(X_1,\ldots,X_{i-1}\).

6.3 Dependency graphs and evaluation order

Each attribute occurrence in the parse tree is a node in a dependency graph. If the rule for attribute \(b\) uses attribute \(a\), draw an edge \(a\to b\): \(b\) depends on \(a\). A valid evaluation order is any topological order of this graph: evaluate a node only after all its predecessors. If the graph has a cycle, the SDD is circular and has no static evaluation order.

Dependencies for 3 * 5 + 4. The value of the root \(E\) depends on the values of its \(E_1\) and \(T\). The value of \(E_1\) depends on its \(T_1\) and \(F\). The value of \(T_1\) depends on the digit 3, and \(F\) on the digit 5. A topological order evaluates the digits first, then the inner \(T\), then \(E_1\), then the outer \(T\), then the root. Any order that respects those edges is correct.

For a large tree, the compiler does not usually build the dependency graph explicitly. It uses a grammar class whose shape guarantees an order: S-attributed definitions evaluate bottom-up; L-attributed definitions evaluate left-to-right depth-first. Those two classes cover most practical translations.

6.4 S-attributed and L-attributed definitions

An SDD is S-attributed if every attribute is synthesized. Then every node depends only on its children, so a bottom-up parse (such as LR) can evaluate attributes as it reduces each production. The semantic actions can be placed at the right end of each production; this is called a postfix translation scheme.

An SDD is L-attributed if every inherited attribute of a child \(X_j\) in \(A\to X_1\cdots X_n\) depends only on attributes of \(A\) and of \(X_1,\ldots,X_{j-1}\), and every synthesized attribute of \(A\) depends only on attributes of \(A\) and its children. The “L” means left-to-right: a depth-first left-to-right traversal can evaluate every attribute once. Every S-attributed SDD is L-attributed, because it has no inherited attributes at all.

Heads-up: “inherited” does not mean “from the parent only.” An inherited attribute of \(X_j\) can depend on the parent \(A\) and on any left sibling \(X_1,\ldots,X_{j-1}\). It cannot depend on a right sibling, because that value would not exist yet in a left-to-right traversal. That restriction is exactly what makes L-attributed definitions evaluable in one pass.

6.5 Syntax-directed translation schemes: actions in the grammar

An SDD is a specification: it says what the attributes are and which rules define them. A syntax-directed translation scheme (SDT) is an implementation: it embeds semantic actions, written in braces, at positions in the right side of productions. The parser executes an action when it reaches that position.

E → E1 + T    { E.val = E1.val + T.val }
E → T         { E.val = T.val }
T → T1 * F    { T.val = T1.val * F.val }
T → F         { T.val = F.val }
F → ( E )     { F.val = E.val }
F → digit     { F.val = digit.lexval }

These actions are at the right end, so they run when the production is reduced. In a bottom-up parser, that is exactly the moment when all the children’s values are available. In a top-down parser, an action in the middle of a production runs after the symbols to its left have been matched and before the symbols to its right are parsed.

Infix to postfix. The same expression grammar can emit postfix instead of computing a value: 
E → E1 + T    { print('+') }
E → T
T → T1 * F    { print('*') }
T → F
F → ( E )
F → digit     { print(digit.lexval) }
For 3 + 4 * 5, the output is 3 4 5 * +. The digits print when their \(F\) productions reduce; the * prints after the \(T_1*F\) subtree is complete; the + prints last. Postfix is a linearization of the tree: operands first, operator after its operands. A stack machine can evaluate it with one pass.

If an action must run in the middle of a production, a bottom-up parser needs a marker: introduce a new nonterminal \(M\to\varepsilon\) with the action attached, and place \(M\) where the action belongs. The parser reduces \(M\) at that point, which executes the action. This is a standard trick, but it is easy to overuse; prefer an S-attributed or L-attributed formulation when possible.

6.6 Left recursion, attributes, and the shape of the tree

Removing left recursion changes the parse tree, so it can change where attributes must flow. For a left-associative operator, the original grammar \(E\to E+T\) naturally accumulates on the left. The transformed grammar \(E\to T E'\), \(E'\to+T E'\mid\varepsilon\) builds a right-leaning tail. If you want the same left-associative value, pass an inherited attribute down the tail:

E  → T R         { R.in = T.val;  E.val = R.out }
R  → + T R1      { R1.in = R.in + T.val;  R.out = R1.out }
R  → ε           { R.out = R.in }

Here R.in is the value accumulated so far, and R.out is the final value. The inherited attribute carries the accumulator down; the synthesized attribute carries the result back up. This is L-attributed and works with a top-down parser. It also shows why “just remove left recursion” is not a purely syntactic trick when semantic actions are involved.

Key. An SDD attaches attributes and rules to a grammar; an SDT embeds actions in productions. Synthesized attributes flow up; inherited attributes flow down or from left siblings. S-attributed definitions evaluate bottom-up; L-attributed definitions evaluate left-to-right. Dependency graphs tell you when an arbitrary definition is evaluable.
Heads-up: an attribute rule is not a runtime statement unless you make it one. In an SDD, \(E.val=E_1.val+T.val\) is a definition of a value, not an instruction with a fixed execution time. The evaluation order comes from the dependency graph or from the S/L class. In an SDT, the braces do denote actions with an execution time. Keep the two levels separate.
Heads-up: inherited attributes can create cycles. A rule that defines \(A.a\) from \(B.b\) and \(B.b\) from \(A.a\) is circular. No topological order exists, and a one-pass evaluator will loop or use a stale value. Check the dependency graph, not just the grammar.

7. Intermediate code and type checking

The parse tree is still close to the source. Code generation wants something closer to a machine: explicit temporaries, explicit jumps, explicit memory operations. The middle form is intermediate representation (IR). A good IR is machine independent, easy to analyze, and easy to translate into many targets.

7.1 Why an IR at all?

  • Retargetability: one front end can feed several back ends. The IR is the contract.
  • Optimization: facts such as “this expression is computed twice” are easier to see and transform in IR than in source or assembly.
  • Explicitness: the tree’s implicit precedence and grouping become ordered instructions with named temporaries.
  • Analysis: control-flow graphs and data-flow equations are defined over IR instructions and basic blocks.

Common IR forms are abstract syntax trees (ASTs), directed acyclic graphs (DAGs) for expressions, three-address code (3AC), quadruples, triples, static single assignment (SSA), and bytecode. They differ in how much structure they keep and how easy they are to analyze. This page uses 3AC and quadruples because they are the book’s main currency and the easiest to write on an exam.

7.2 Three-address code

Three-address code is a sequence of instructions of the form \(x=y\ \text{op}\ z\), plus copies, jumps, calls, and memory operations. “Three-address” means at most three names: two sources and one destination. A complex expression is broken into temporaries.

From expression to 3AC. For x = a*b + c*d: 
t1 = a * b
t2 = c * d
t3 = t1 + t2
x  = t3
Each instruction has one operator. The temporaries \(t_1,t_2,t_3\) are compiler-generated names. A later optimizer may eliminate \(t_3\) by writing x = t1 + t2, or eliminate \(t_1\) if it is used once.

7.4 Translating control flow

Control flow is where 3AC earns its keep. A conditional branch has a target label; an unconditional branch closes the current path. The exact labels are arbitrary, but the shape matters.

If–else. For 
if (a < b) x = 1; else x = 2;
one translation is: 
    if a < b goto L1
    goto L2
L1: x = 1
    goto L3
L2: x = 2
L3:
The first branch selects the then-part; the unconditional goto L2 skips it when the condition is false. L3 is the join point.
While. For 
while (a < b) S;
one translation is: 
L1: if a < b goto L2
    goto L3
L2: S
    goto L1
L3:
The condition is tested at the top. The back edge goto L1 is what makes it a loop. A do–while would put the test at the bottom and enter the body unconditionally.

Boolean expressions with short-circuit evaluation need more care. In a < b && c < d, if the first comparison is false, the second must not be evaluated (it may have side effects or divide by zero). One translation into a temporary truth value is:

    if a < b goto L1
    t = 0
    goto L2
L1: if c < d goto L3
    t = 0
    goto L2
L3: t = 1
L2:

For ||, the true branch jumps directly to t = 1. In a real compiler, the boolean value is often not materialized at all: the jumps are threaded directly into the surrounding if or while. That is what the true/false lists in the next subsection represent.

7.5 Backpatching: generate jumps before you know the target

A one-pass translator emits instructions before it knows where later code will start. For a forward jump, the target label is unknown at emission time. Backpatching solves this by emitting a jump with an empty target and keeping a list of the instruction indices that need that target. When the target becomes known, fill it in.

Three operations are enough:

  • makelist(i) creates a list containing instruction index \(i\).
  • merge(p1, p2) concatenates two lists of jump indices.
  • backpatch(p, target) fills target into the target field of every jump in list \(p\).

For a boolean expression \(E\), keep E.trueList (jumps to take when \(E\) is true) and E.falseList (jumps to take when \(E\) is false). For a statement \(S\), keep S.nextList (jumps that must go to the statement after \(S\)).

The rules for if and while.
  • \(S\to\textbf{if }(E)\ S_1\): backpatch \(E.trueList\) to the start of \(S_1\); \(S.nextList = \text{merge}(E.falseList, S_1.nextList)\).
  • \(S\to\textbf{if }(E)\ S_1\ \textbf{else}\ S_2\): backpatch \(E.trueList\) to the start of \(S_1\), \(E.falseList\) to the start of \(S_2\); \(S.nextList = \text{merge}(S_1.nextList, S_2.nextList)\).
  • \(S\to\textbf{while }(E)\ S_1\): backpatch \(S_1.nextList\) to the start of the condition, \(E.trueList\) to the start of \(S_1\); \(S.nextList = E.falseList\).
A marker nonterminal \(M\to\varepsilon\) can record the current instruction index as M.instr, which is how the start of the condition or body is remembered without a separate pass.
Boolean operators, list-style. For \(E\to E_1\ \&\&\ E_2\): backpatch \(E_1.trueList\) to the start of \(E_2\); \(E.trueList=E_2.trueList\); \(E.falseList=\text{merge}(E_1.falseList,E_2.falseList)\). For \(E\to E_1\ ||\ E_2\): backpatch \(E_1.falseList\) to the start of \(E_2\); \(E.falseList=E_2.falseList\); \(E.trueList=\text{merge}(E_1.trueList,E_2.trueList)\). For \(E\to !E_1\), swap the lists. The short-circuit semantics is encoded in which list is patched where.

7.6 Expression DAGs and local value numbering

A DAG for an expression shares identical subexpressions. For a + a*(b-c) + (b-c)*d, the subexpression b-c appears twice but is one node in the DAG; the leaf a is also shared. The DAG is smaller than the tree and makes common subexpressions visible.

        +
      /   \
     +     *
    / \   / \
   a   *  S   d
      / \
     a   S

Here \(S\) stands for the single shared node \(b-c\). It is drawn once in the DAG; the two edges into \(S\) are two uses of the same value.

The same idea works for a basic block. Value numbering assigns a number to every distinct value. Leaves get numbers by name; each operation gets a key (operator, child numbers). If the key already exists, the result is the existing number; otherwise it is a new number. Identical keys mean identical computations, so the later one can be replaced by a copy or deleted.

Value numbering on a block. 
a = b + c
d = b + c
e = a + d
Number b as 1, c as 2. The first b+c gets number 3 and defines a as 3. The second b+c has the same key (+,1,2), so d also gets 3. Then a+d is (+,3,3), a new number 4 for e. The second addition is redundant; if d is not used later, it can be deleted. If a and d are both used, one can be replaced by the other.

This is local common-subexpression elimination: it works within one basic block, where the straight-line order makes “the same value” easy to track. The global version needs available-expression analysis, covered in Section 10.7.

Key. 3AC makes operations and temporaries explicit; quadruples name results, triples use positions, indirect triples add a reorderable pointer table. Control flow becomes labels and jumps; backpatching fills forward jumps later. A DAG or value numbering removes repeated computations inside a block.
Heads-up: a DAG is not a control-flow graph. A DAG summarizes values inside one straight-line block. A CFG summarizes which blocks can execute after which. They answer different questions and are used by different optimizations.
Heads-up: deleting a “redundant” assignment is safe only if it has no side effects and its result is truly unused. A function call, a volatile load, or a store can change memory even if its returned value is ignored. Value numbering must not treat those as pure arithmetic.

7.7 Type expressions and type systems

A type is a set of values plus the operations that make sense on them. A type expression is a syntactic description of a type. The usual grammar is:

\[ T \to \texttt{basic} \mid \texttt{array}(T,n) \mid \texttt{pointer}(T) \mid T_1\times T_2 \mid \texttt{function}(T_1,\ldots,T_n)\to T \mid \alpha \]

Here basic is a base type such as int, float, char, or bool; array(T,n) is an array of \(n\) elements of type \(T\); pointer(T) is a pointer to \(T\); \(T_1\times T_2\) is a product, used for records and parameter lists; function(...) is a function type; and \(\alpha\) is a type variable, used during inference.

Static checking is conservative: it may reject a program that would have run correctly, because it cannot prove that a dynamic condition always holds. A sound type system never accepts a program that can commit a type error; a complete one accepts every program that cannot. For a Turing-complete language, no decidable checker can be both sound and complete for “never commits a type error”; practical systems choose soundness and accept some false alarms, or choose flexibility and use run-time checks.

7.8 Type equivalence: structural versus name

Two types are structurally equivalent if they have the same structure after resolving type names: the same base type, or the same constructor applied to equivalent components. Two types are name equivalent if they come from the same type declaration (or are the same primitive type).

The difference in one example. 
type A = int;
type B = int;
A x;
B y;
Under structural equivalence, x and y have the same type, because both resolve to int. Under strict name equivalence, A and B are distinct type names, so they are different. Many languages treat typedef as a transparent alias, which makes A and B compatible; Ada’s type A is Integer; creates a distinct type, so they are not. The rule depends on the language, not on the word “typedef.”

For arrays, structural equivalence compares element type and size (and sometimes index type). For functions, it compares parameter types, parameter order, and return type. For records, it compares field names, field types, and sometimes order. Name equivalence is easier to check and gives stronger abstraction; structural equivalence is more flexible and matches “duck typing” intuitions.

7.9 Type inference and unification

Type inference computes types without explicit declarations. A common engine is unification: represent unknown types by type variables, write equations from the way values are used, and solve the equations by substitution.

The unification algorithm maintains a substitution from type variables to type expressions. To unify \(T_1\) and \(T_2\):

  • If both are the same basic type or the same type constructor with equal arguments, succeed.
  • If one is a type variable \(\alpha\), bind \(\alpha\) to the other type, provided \(\alpha\) does not occur inside that type (the occurs check).
  • If both are constructors, unify their components pairwise.
  • Otherwise, fail.
Unify a function type. Suppose \(f\) has type \(\alpha\to\beta\) and is applied to an int, producing a \(\gamma\). The application imposes \(\alpha=\texttt{int}\) and \(\beta=\gamma\). The substitution is \(\{\alpha\mapsto\texttt{int},\ \beta\mapsto\gamma\}\). If later the result is used as a float, unify \(\gamma=\texttt{float}\), giving \(f:\texttt{int}\to\texttt{float}\).
Occurs check. Unifying \(\alpha\) with \(\texttt{int}\to\alpha\) would require an infinite type: \(\alpha=(\texttt{int}\to(\texttt{int}\to\cdots))\). The occurs check rejects it. Without the check, the algorithm would loop or build a cyclic structure.

A classic inference example is a length function:

length []       = 0
length (x : xs) = 1 + length xs

The empty-list case says the argument is a list of some type \(\alpha\), and the result is an integer. The cons case says the argument is a list of the same type as the head, and the recursive call has the same type as the whole. Unification yields \(\texttt{length}:\texttt{list}(\alpha)\to\texttt{int}\), polymorphic in \(\alpha\). No run-time type test is needed.

7.10 Coercion, overloading, and polymorphism

  • Coercion is an implicit conversion inserted by the compiler. Widening an int to a float is usually safe; narrowing a float to an int loses information and is often an explicit cast. In IR, a coercion becomes an instruction such as inttofloat.
  • Overloading lets one name have several types, such as + for integers and floats. The checker resolves the overload from the operand types and context. If two resolutions are equally valid, the expression is ambiguous and must be rejected or annotated.
  • Parametric polymorphism lets one implementation work uniformly for all types, as in length : list α → int. Ad hoc polymorphism is overloading: different implementations for different types. They look similar in source but are different mechanisms.

Type checking an expression such as a + b is therefore not just “are both numeric?” It is: look up the declared types, resolve the overload, check that a common type exists, insert coercions if the language allows them, and produce the result type. If the language has subtyping, the rule is “the operands must have a common supertype that supports the operation,” which is a different and more complex check.

7.11 Symbol tables: the compiler’s name memory

A symbol table maps names to declarations. A typical entry stores the name, kind (variable, function, type, label), type, storage class and location, scope, and source position. The table is usually a hash table for fast lookup, with a stack of scopes for nested blocks.

Nested scopes. 
int x;
{
    float x;
    x = 1.0;     // the inner float x
}
x = 2;           // the outer int x
Entering the block pushes a scope; declaring float x inserts into the inner scope and shadows the outer. Lookup searches the innermost scope first, then outward. Leaving the block pops the inner scope; the outer x is visible again. A hash table with a scope stack can implement this by chaining entries and restoring the previous binding on exit.

Symbol tables are used at every stage. The lexer may install identifiers; the parser may distinguish keywords; semantic analysis looks up types and checks declarations; code generation reads storage locations. Some compilers keep separate namespaces for variables, labels, struct tags, and member names, because the same spelling can mean different things in different contexts.

Forward references need special handling. If a function calls a function declared later, the compiler either makes two passes, or inserts a placeholder and patches the type/location when the declaration is seen. The symbol table entry is the natural place to hold “declared but not yet defined.”

Here is the shape of the rules, not a full language. The attribute type is synthesized; lookup reads the symbol table; widen inserts a conversion when the language permits it.

These rules are simple individually; the engineering is in handling errors, coercions, overloads, and scopes without cascading false errors.

7.13 Array addressing: from subscript to byte offset

An array is stored as a contiguous block. For a one-dimensional array \(A[\ell..u]\) with element size \(w\), the address of \(A[i]\) is

\[ \text{base} + (i-\ell)\times w. \]

For a two-dimensional array \(A[\ell_1..u_1,\ell_2..u_2]\) stored in row-major order, row by row, the address of \(A[i_1,i_2]\) is

\[ \text{base} + \bigl((i_1-\ell_1)\,n_2 + (i_2-\ell_2)\bigr)\times w,\qquad n_2=u_2-\ell_2+1. \]

For column-major order, column by column, swap the roles:

\[ \text{base} + \bigl((i_2-\ell_2)\,n_1 + (i_1-\ell_1)\bigr)\times w,\qquad n_1=u_1-\ell_1+1. \]
3AC for x = A[i,j], row-major, lower bounds zero. 
t1 = i * n2
t2 = t1 + j
t3 = t2 * w
t4 = base_A + t3
x  = *t4
If the lower bounds are not zero, subtract \(\ell_1\) and \(\ell_2\) before the multiply/add. If bounds checking is enabled, compare \(i\) and \(j\) with their low/high bounds and branch to an error handler before the load.

Array descriptors usually store the base address, the lower and upper bounds of each dimension, the element size, and the stride for each dimension. A struct field is simpler: its address is the struct base plus a fixed offset computed from the field layout and alignment. Pointer arithmetic scales by the size of the pointed-to type: p + 1 means “the next element,” not “the next byte.”

Key. Types are checked against declarations and operations; equivalence can be structural or by name; inference solves type equations by unification; coercion inserts conversions; overloading chooses among types. The symbol table supplies the declarations, and array addressing turns subscripts into byte offsets.
Heads-up: type equivalence and type compatibility are not the same. Two types can be different but compatible through a coercion or a subtype relationship. A checker may accept int + float by widening, even though int and float are not equivalent. State which relation the question asks for.
Heads-up: row-major versus column-major changes the multiplier. Row-major multiplies the first index by the number of columns; column-major multiplies the second index by the number of rows. Mixing them up is the most common array-addressing error.

8. Runtime environments: where values live

An intermediate representation talks about names and temporaries. At run time, those names have to become memory locations: registers, stack slots, global addresses, or heap objects. The runtime environment is the organization that makes this mapping work: storage areas, activation records, links between frames, and the rules for finding a nonlocal variable.

Scope is not lifetime. Scope is a compile-time, textual property: where a name is visible. Lifetime is a run-time property: when the storage exists. A static local variable has block scope but whole-program lifetime. A heap object can outlive the function that created it and be reachable through a pointer. A local variable can go out of scope while a pointer to it still exists — that is a dangling pointer, not a scoping rule.

8.2 Activation records: the frame of one call

Every active call has an activation record (also called a frame). It holds everything that call needs:

  • Actual parameters (or pointers to them, depending on the calling convention).
  • Return address: where to continue when the call returns.
  • Saved machine state: registers the callee must restore, sometimes condition codes.
  • Control link (dynamic link): a pointer to the caller’s frame.
  • Access link (static link): a pointer to the frame of the lexically enclosing function, when the language has nested functions.
  • Local variables and compiler temporaries.

The order of fields is a convention, not a law. Some architectures put parameters in registers; some put the return address in a link register; some grow the stack upward. What matters is that the compiler and the calling convention agree on where each item is.

8.3 The calling sequence

A call is a small protocol between caller and callee:

  1. Caller: evaluate the arguments, place them where the convention says (stack slots or registers), save the return address, and jump to the callee.
  2. Callee: save the old frame pointer and any callee-saved registers, set up its own frame pointer, allocate space for locals and temporaries, and run.
  3. Return: put the result where the convention says, restore saved registers and the old frame pointer, pop the frame, and jump back to the return address.
  4. Caller: reclaim the argument space if it is responsible for it, and use the result.

The frame pointer (FP) gives a stable reference point inside the frame, so locals can be addressed at fixed offsets even if the stack pointer moves during expression evaluation. The stack pointer (SP) marks the current top. A compiler may omit the frame pointer and use SP-relative offsets when the frame size is fixed; debuggers and profilers often prefer a frame pointer because it makes stack unwinding easier.

Recursion. A recursive call does not reuse the caller’s locals. Each call pushes a new frame with its own copy of parameters and locals. When the call returns, its frame is popped and the caller’s frame is intact. This is why a recursive function can have many “versions” of the same variable alive at once, one per activation.

8.4 Static, stack, and heap allocation

Static allocation gives an object a fixed address determined at compile or load time. Globals and static locals live here. It is simple and fast, but it cannot support recursion or dynamically sized data, because the number of simultaneous activations is not known in advance.

Stack allocation gives each activation a frame pushed on call and popped on return. It matches the LIFO (last-in, first-out) shape of calls and supports recursion naturally. The limitation is lifetime: a stack object dies when its frame is popped. Returning a pointer to a local, or storing it somewhere that outlives the call, leaves a dangling reference.

Heap allocation gives an object a lifetime independent of the call stack. The program requests space at run time; the object remains until explicitly freed or garbage-collected. Heap allocation supports dynamic data structures (linked lists, trees, closures), but it costs allocation time and requires memory management.

Heads-up: “the compiler puts locals on the stack” is not universal. Locals that are captured by a closure, or whose address escapes, may be allocated on the heap. An optimizing compiler may keep a local in a register for its whole live range, or scalar-replace an object. The source-level lifetime rule is what matters; the storage decision is an implementation strategy.

8.5 Lexical scope versus dynamic scope

Lexical scope (static scope) resolves a name by its position in the source text: the innermost enclosing declaration wins. Dynamic scope resolves a name by the current call chain: the most recent active declaration wins. Most modern languages use lexical scope because it makes programs easier to reason about and allows compile-time resolution.

The same program, two answers. 
int x = 1;
void f() { print(x); }
void g() { int x = 2; f(); }
g();
Under lexical scope, f was declared next to the global x, so it prints 1. Under dynamic scope, f is called from g, whose local x is active, so it prints 2. The source text is identical; the name-resolution rule is different.

Lexical scope is implemented with the access link: a pointer from the current frame to the frame of its lexical parent. Dynamic scope is implemented by searching the control links (the caller chain) at run time. This is the cleanest way to remember which link does what:

\[ \text{access link} \to \text{lexical parent}, \qquad \text{control link} \to \text{caller}. \]

8.6 Access to nonlocal variables

In a language with nested functions, an inner function can refer to a variable of an outer function. The compiler knows the lexical depth of each declaration: global scope is depth 0, a function body is depth 1, a nested function is depth 2, and so on. To reach a variable at depth \(k\) from a frame at depth \(d\), follow \(d-k\) access links.

An access-link chain. 
void outer() {
    int x = 10;
    void middle() {
        void inner() { print(x); }
        inner();
    }
    middle();
}
outer is at depth 1, middle at depth 2, inner at depth 3. When inner runs, its access link points to middle’s frame; middle’s access link points to outer’s frame. To find x, inner follows two access links. The control link would lead to whoever called inner, which may not be its lexical parent.

The access-link chain costs \(O(d)\) per nonlocal access in the worst case. A display is an array indexed by lexical depth that stores the current frame pointer for each depth. Then a nonlocal access is one array lookup. The display is updated on call and restored on return; it trades a small amount of bookkeeping for faster access.

If an inner function escapes its defining scope — for example, it is returned as a closure and called later — the stack frame it refers to may be gone. A language with closures must keep the captured environment alive, typically by allocating it on the heap and storing a pointer in the closure. This is the same lifetime problem as returning a pointer to a local, seen at the level of functions.

Key. Code and static data last for the program; stack frames last for one activation; heap objects last until freed or unreachable. The activation record holds parameters, return address, saved state, links, locals, and temporaries. Lexical scope uses access links; dynamic scope follows control links.
Heads-up: the control link and the access link are not interchangeable. The control link points to the caller. The access link points to the lexically enclosing function. In a language without nested functions, they may coincide in simple cases, but confusing them breaks nonlocal access and closures.

8.7 Parameter passing: five different contracts

“Pass by value” and “pass by reference” are not the only options, and the differences are semantic, not just implementation details. The parameter mode decides what the callee receives, when the argument is evaluated, and whether writes are visible to the caller.

In f, the parameter is a local copy; assigning 99 changes the copy, not a. In g, the parameter is an alias for a; assigning through it changes a.

Call-by-value-result (copy-in/copy-out) was designed to give the callee a local copy, like call-by-value, but to copy the final value back on return, like reference. It is not equivalent to reference when the same object is passed twice or when the argument is also reachable another way. The copy-out order matters.

The classic call-by-name surprise. Suppose a swap procedure has call-by-name parameters, and the caller writes 
int i = 0;
int a[2] = {10, 20};
swap(i, a[i]);
Inside the procedure, x stands for the expression i and y stands for the expression a[i]. The body t = x; x = y; y = t becomes: t = 0; then i = a[i], which sets i = 10; then a[i] = 0, which now writes a[10], not a[0]. The second use of y re-evaluated its expression after i changed. With call-by-reference, y would be bound to the address of a[0] at call time, so this particular surprise does not occur — but references still create aliases, as in f(a, a) with two reference parameters. With value-result, copy-out order can matter when the arguments alias.

Call-by-name substitutes the argument expression textually for each use of the parameter. If the expression has side effects, those effects happen on every use. It can implement short-circuit-like behavior and lazy evaluation, but it is hard to reason about and hard to optimize. Call-by-need evaluates the thunk on first use and caches the result; it gives laziness without repeated work. Haskell uses call-by-need.

Heads-up: “Java passes objects by reference” is imprecise. Java passes the object reference by value: the callee gets a copy of the reference. It can mutate the object both refer to, but it cannot make the caller’s variable point to a different object. C passes arrays as pointers to their first element, so array parameters behave like references even though scalar parameters are by value. State the language and the mode, not just the word “reference.”
Heads-up: argument evaluation order can matter. In C, the order of evaluation of function arguments is unspecified. If two arguments modify the same object, the program may have undefined behavior. A compiler optimization must respect the language’s sequencing rules, not assume left-to-right.

8.8 Heap management: allocation, fragmentation, and collection

The heap is a pool of memory managed at run time. An allocator must find a free block of the requested size, return it, and later accept it back. The classic strategies are:

  • First-fit: take the first free block large enough. Fast, but can leave small fragments near the front.
  • Best-fit: take the smallest free block large enough. Less wasted space per allocation, but slower to search and can leave many tiny unusable fragments.
  • Worst-fit: take the largest free block. Leaves a large remainder, but tends to break up large free areas.

Internal fragmentation is wasted space inside an allocated block (for example, rounding a request up to an alignment boundary). External fragmentation is free space split into many small blocks that cannot satisfy a large request even though the total free space is enough. Coalescing merges adjacent free blocks on free; boundary tags or segregated free lists make this practical.

8.9 Garbage collection: reclaim what can never be used again

An object is garbage if it is unreachable from the program’s roots: registers, stack slots, global variables, and any other live starting points. Reachability is an approximation of “will never be used again”; a conservative collector may retain an object that is actually dead, which is safe but wastes memory. A precise collector knows exactly which words are pointers.

Heads-up: a memory leak is not always a missing free. In a garbage-collected language, an object can be reachable from a root but no longer needed — a cache that grows forever, a listener that is never removed, a global list that keeps everything alive. That is a semantic leak; the collector is doing its job.
Heads-up: returning a pointer to a local is a lifetime error, not a type error. The type system may say int*, but the storage is gone when the frame is popped. The same issue appears when a closure captures a stack frame that has returned; the environment must be heap-allocated or otherwise kept alive.

9. Basic blocks, CFGs, and local optimization

Optimization needs a unit of analysis. The first unit is the basic block: a straight-line sequence of instructions with one entry and one exit. Inside a block, control never branches except at the end, so the order of instructions is fixed. That makes local reasoning easy: if two instructions compute the same expression and nothing between them changes the operands, the second computation is redundant.

9.1 Leaders and basic blocks

To split a program into basic blocks, find the leaders:

  1. The first instruction is a leader.
  2. Every instruction that is the target of a jump is a leader.
  3. Every instruction immediately after a jump (conditional or unconditional) is a leader.

A basic block starts at a leader and ends just before the next leader. Its last instruction is a branch, a return, or an ordinary instruction that falls through to the next block. If control can fall through from one block to the next, there is an edge between them.

A loop, split into blocks. 
    i = 1
    sum = 0
L1: if i > 10 goto L2
    sum = sum + i
    i = i + 1
    goto L1
L2: ...
Leaders: the first instruction; L1 (jump target); sum = sum + i (instruction after the conditional jump); L2 (jump target). The blocks are:
  • B1: i = 1; sum = 0
  • B2: L1: if i > 10 goto L2
  • B3: sum = sum + i; i = i + 1; goto L1
  • B4: L2: ...
The CFG edges are B1→B2; B2→B4 when the condition is true; B2→B3 when it is false; B3→B2 (the back edge); B4→exit.
        B1
        |
        v
        B2  --true-->  B4
        |               |
     false              v
        v             exit
        B3
        |
        +---- back to B2

The control-flow graph (CFG) has basic blocks as nodes and possible control transfers as edges. It is the data structure behind almost every global analysis. A CFG may have a unique entry and a unique exit; if the source has multiple returns, a synthetic exit node can collect them. Unreachable blocks are blocks with no path from entry; they can be removed, but only after checking that they contain no required side effects or error behavior.

9.2 What “local” buys you

A local optimization looks at one basic block and nothing else. It does not need to know which branches led to the block or which blocks follow. This makes it fast and safe, but limited: it cannot see that an expression is computed in two different predecessors, or that a variable is dead on every path to the exit. Those are global questions, answered by data-flow analysis in Section 10.

9.3 Constant folding and constant propagation

Constant folding evaluates an operation whose operands are compile-time constants. Constant propagation replaces a use of a variable with a known constant. Locally, both can be done in one forward pass over the block.

A block that collapses. 
x = 2 * 3
y = x + 0
z = y * 1
w = z * 8
Fold 2*3 to 6, so x=6. Propagate 6: y=6+0, fold to 6. Propagate: z=6*1=6. Propagate: w=6*8=48. If none of x,y,z is used later, the block reduces to w=48 (and possibly nothing, if w is also dead). The algebra is simple; the hard part is knowing when a variable really holds the constant on every path.

Algebraic identities simplify expressions using laws such as \(x+0=x\), \(x-0=x\), \(x\cdot1=x\), \(x/1=x\), \(x-x=0\), and \(x\cdot0=0\). These are not universally safe. Floating-point \(x+0\) is not the identity for \(x=-0.0\) under IEEE rules, \(x\cdot0\) is not zero for NaN or infinity, and signed integer overflow is undefined in C/C++. A compiler applies an identity only when the language semantics guarantee it, or when it can prove the exceptional cases cannot occur.

9.4 Strength reduction

Strength reduction replaces an expensive operation with a cheaper equivalent. Multiplication by a power of two can become a shift: \(x*8\) becomes \(x\ll 3\). Multiplication by a small constant can become additions: \(x*3\) becomes \(x+x+x\) (not always faster; the target matters). Division by a power of two can become a shift for unsigned or known-nonnegative values; for signed values, rounding toward zero and negative numbers make the simple shift wrong.

Address arithmetic is the classic case. In a loop over an array, A[i] is base + i*w. Instead of multiplying by w every iteration, keep a pointer p that starts at base and add w each iteration. The multiplication disappears from the loop; the pointer increment is the strength-reduced form. This is also called induction-variable strength reduction.

9.5 Copy propagation and dead code

Copy propagation replaces uses of a variable that was assigned from another variable. If x = y and x is not redefined before z = x + 1, the second instruction can become z = y + 1. If x then has no uses, the copy is dead and can be removed. The safety condition is that y has not been redefined between the copy and the use, and that x has not been redefined.

Dead code elimination removes an instruction whose result is never used and whose execution has no observable side effect. A store to a local variable that is never read again is dead. A store through a pointer may not be dead, because it may alias a location someone else reads; a function call may have side effects; a division by zero may raise an exception. Liveness analysis (Section 10.5) is the systematic way to know which variables are live at each point.

9.6 Common-subexpression elimination with a DAG

Inside a block, if the same expression is computed twice with the same operand values and nothing changes in between, the second computation can reuse the first result. A DAG makes this visible: identical subexpressions become one node with multiple parents. Value numbering is the algorithmic version.

Local CSE. 
a = b + c
d = b + c
e = a + d
The two b+c computations are identical. Value numbering gives both the same number; one can be replaced by a copy, or the second can be deleted if its destination is not needed. If a and d are both live, the block can become: 
a = b + c
d = a
e = a + d
and then copy propagation can simplify e = a + a. If d is not used, the copy disappears too.

For a whole basic block, the DAG construction is:

  1. Create leaves for variables and constants.
  2. For each instruction, create or find an operator node whose children are the value nodes of its operands. If an identical node exists, reuse it; otherwise create it.
  3. Attach the destination variable to the result node. A later assignment to the same variable creates a new node and detaches the old value.
  4. After the block, emit the nodes in a topological order, skipping nodes with no live output. This reconstructs optimized code.

The DAG is a local value graph, not a control-flow graph. It assumes the block executes straight through. If an operand is redefined, the later computation is a different node even if the operator is the same.

9.7 Peephole optimization

Peephole optimization looks at a small sliding window of target instructions and replaces a pattern with a cheaper one. It is local, machine-specific, and often iterative: a rewrite can expose another rewrite. Typical patterns:

  • Remove a jump to the immediately following label: goto L; L: becomes nothing.
  • Remove redundant load/store pairs when the value is already in a register.
  • Replace push R; pop R with nothing.
  • Replace multiplication by a small constant with a shift or an add, when the target allows it.
  • Simplify x = x + 0 or x = x * 1 only when the target arithmetic guarantees the identity; IEEE signed zero and NaNs can break it.
  • Thread jumps: if goto L1 and L1: goto L2, jump directly to L2 (provided no observable label semantics intervene).

Peephole optimization is not a substitute for global analysis. It can miss a redundancy spread across two blocks, and it can be fooled by aliasing or by instructions with side effects. Its advantage is that it is cheap and captures the small inefficiencies that code generators naturally produce.

Key. Leaders define basic blocks; blocks and edges form the CFG. Local optimization works inside one block: fold constants, propagate copies, simplify identities, reduce strength, eliminate dead code, and reuse common subexpressions via a DAG. Peephole optimization is a small-window, target-specific cleanup.
Heads-up: “local” CSE cannot see across a branch. If b+c is computed in both the then-block and the else-block, a local DAG will not remove one; they are different blocks. Global CSE needs available-expression analysis and a way to name the shared value across paths.
Heads-up: algebraic identities are not always identities. Floating-point signed zeros, NaN, infinities, and signed integer overflow break the algebra taught in school. A transformation that is valid for mathematical integers may be invalid for machine integers or IEEE floats. Check the language’s semantics before applying it.

10. Data-flow analysis: facts that flow through the graph

A local optimization sees one basic block. A global optimization needs to know facts at every point in the CFG: which definitions can reach this use, which variables are still needed, which expressions have already been computed on every path, which variables hold constants. Data-flow analysis is the general method for computing those facts. It sets up equations over the CFG and solves them by iteration to a fixed point.

10.1 The four questions every analysis answers

QuestionWhat it decides
DirectionDoes information flow forward (from entry to exit) or backward (from exit to entry)?
May or mustIs a fact possible on some path (union), or guaranteed on every path (intersection)?
Transfer functionHow does one basic block change the incoming facts? Usually gen adds facts and kill removes facts.
Initial valuesWhat do we assume at the entry or exit before iteration? This determines which fixed point we compute.

Once you can answer those four, the equations almost write themselves. The rest is bookkeeping: iterate until nothing changes, and make sure the iteration terminates.

10.2 The lattice picture

A data-flow analysis has a set of possible facts called a domain, and a way to combine facts from different paths. The domain is usually a finite lattice: a partially ordered set in which every pair of elements has a greatest lower bound (meet) and a least upper bound (join). The height of the lattice is the length of the longest chain; finite height is what guarantees termination.

For a powerset domain, the order is set inclusion. The bottom is \(\varnothing\), the top is the universal set \(U\). Union and intersection combine facts:

\[ \text{may analysis: combine by union }(\cup), \qquad \text{must analysis: combine by intersection }(\cap). \]

The Dragon Book calls the combining operator the meet operator, even when it is union. Do not let the name mislead you: what matters is whether the analysis asks “on some path” or “on every path.”

For constant propagation, the domain is different: each variable can be \(\top\) (no information yet), a specific constant \(c\), or \(\bot\) (not a constant, because paths disagree). The meet table is:

\(\sqcap\)\(\top\)\(c\)\(d\)\(\bot\)
\(\top\)\(\top\)\(c\)\(d\)\(\bot\)
\(c\)\(c\)\(c\)\(\bot\)\(\bot\)
\(d\)\(d\)\(\bot\)\(d\)\(\bot\)
\(\bot\)\(\bot\)\(\bot\)\(\bot\)\(\bot\)

Here \(c\neq d\). Start at \(\top\) and move downward as information arrives: a single constant is more informative than “unknown,” and a conflict is the most conservative result. This is a different lattice from the powerset one, but the fixed-point idea is the same.

Why iteration terminates. Each step of the analysis moves a value along the lattice in one direction: upward for a may analysis that starts at bottom, downward for a must analysis that starts at top. The lattice has finite height, and the transfer functions are monotone (more input facts cannot produce fewer output facts in the direction of travel). A monotone sequence in a finite-height lattice cannot change forever, so the iteration reaches a fixed point.

10.3 The worklist algorithm

For a forward analysis, the equations are:

\[ \mathrm{IN}[B]=\bigsqcup_{P\in\mathrm{pred}(B)}\mathrm{OUT}[P],\qquad \mathrm{OUT}[B]=f_B(\mathrm{IN}[B]). \]

For a backward analysis, reverse the arrows:

\[ \mathrm{OUT}[B]=\bigsqcup_{S\in\mathrm{succ}(B)}\mathrm{IN}[S],\qquad \mathrm{IN}[B]=f_B(\mathrm{OUT}[B]). \]

The symbol \(\sqcup\) is the combination operator: union for may, intersection for must. A worklist implementation avoids recomputing the whole graph after every change:

initialize IN/OUT for every block
worklist = all blocks
while worklist is not empty:
    remove a block B
    recompute IN[B] from predecessors (forward)
    recompute OUT[B] from IN[B] and the transfer function
    if OUT[B] changed:
        add every successor of B to the worklist

For a backward analysis, recompute OUT from successors, then IN, and add predecessors when IN changes. The order of removal affects speed, not the final fixed point. A reverse-postorder traversal usually converges faster because it follows the flow of information.

10.4 Reaching definitions

A definition is an instruction that assigns to a variable. A definition \(d\) reaches a point \(p\) if there is a path from \(d\) to \(p\) on which the variable is not redefined. Reaching definitions is a forward may analysis: a definition reaches if it can reach on some path, so the combination is union.

For each block \(B\):

  • \(\mathrm{gen}[B]\): definitions inside \(B\) that reach the end of \(B\). If a variable is defined several times in \(B\), only the last definition reaches the end; earlier ones are killed inside the block.
  • \(\mathrm{kill}[B]\): all definitions of variables that are defined in \(B\), except the ones in \(\mathrm{gen}[B]\). These are the definitions from other blocks that cannot survive past \(B\).

The equations are:

\[ \mathrm{IN}[B]=\bigcup_{P\in\mathrm{pred}(B)}\mathrm{OUT}[P],\qquad \mathrm{OUT}[B]=\mathrm{gen}[B]\cup(\mathrm{IN}[B]-\mathrm{kill}[B]). \]

Initialize \(\mathrm{OUT}[B]=\varnothing\) for every block; the entry block has no predecessors, so \(\mathrm{IN}[\text{entry}]=\varnothing\). The iteration moves sets upward by union.

A branch example.

B2: if x > 0 goto B4
B3: d3: y = 3
    goto B5
B4: d4: y = 4
B5: d5: z = y
The definitions are \(d_1\) (x), \(d_2,d_3,d_4\) (y), and \(d_5\) (z).

At the entry of B5, the definitions of \(y\) that reach are \(d_3\) and \(d_4\); \(d_2\) was killed on both branches. \(d_1\) still reaches because neither branch redefines \(x\). \(d_5\) is generated inside B5, so it is in OUT but not IN.
Heads-up: a definition can be killed on one path and still reach on another. Reaching definitions is a may analysis: the union of predecessor OUT sets keeps a definition alive if any path preserves it. Do not intersect the predecessor sets; that would be a must analysis and would lose valid reaching facts.
Heads-up: gen is not “every definition in the block.” If a block contains x=1; x=2, only the second definition reaches the end; the first is killed inside the block. Computing gen as “all definitions” would make the analysis claim a dead definition reaches later code.

10.5 Live variables

A variable \(x\) is live at a program point if there is a path from that point to the exit on which \(x\) is used before it is defined. Liveness is a backward may analysis: it looks toward the future, and a variable is live if some path uses it. It is the basis for dead-code elimination and register allocation.

For each block \(B\):

  • \(\mathrm{use}[B]\): variables used in \(B\) before any definition in \(B\).
  • \(\mathrm{def}[B]\): variables defined in \(B\) before any use in \(B\).

The equations run backward:

\[ \mathrm{OUT}[B]=\bigcup_{S\in\mathrm{succ}(B)}\mathrm{IN}[S],\qquad \mathrm{IN}[B]=\mathrm{use}[B]\cup(\mathrm{OUT}[B]-\mathrm{def}[B]). \]

Initialize \(\mathrm{IN}[B]=\varnothing\) for all blocks and \(\mathrm{OUT}[\text{exit}]=\varnothing\). The union over successors is the “some path” part; subtracting \(\mathrm{def}[B]\) stops a variable from being live before a definition that kills it.

Liveness on the branch example. The same CFG: 
B1: d1: x = 1
    d2: y = 2
B2: if x > 0 goto B4
B3: d3: y = 3
    goto B5
B4: d4: y = 4
B5: d5: z = y

Read it backward. At the exit of B5, nothing is live. B5 uses \(y\), so \(y\) is live at B5’s entry; \(z\) is defined but never used, so \(z\) is dead. B3 and B4 both define \(y\), so \(y\) is not live at their entries; the use in B5 is already satisfied by those definitions. B2 uses \(x\), so \(x\) is live at B2’s entry and at B1’s exit. B1 defines \(x\), so \(x\) is not live at B1’s entry. The assignment \(y=2\) in B1 is dead because both branches redefine \(y\) before B5 uses it.

Liveness gives interference: two variables interfere if both are live at the same program point. In a register allocator, interfering variables cannot share a register; the interference graph is colored with the number of available registers. It also gives a precise dead-code test: an assignment to \(x\) is dead if \(x\) is not live immediately after the assignment (and the assignment has no other side effect).

Heads-up: liveness is about the future, not the past. A variable that was used earlier is not necessarily live now. A variable that is defined but never used again is dead even if it was live before the definition. Always ask: “from here to the exit, is there a use before the next definition?”
Heads-up: use and def are “before any” sets. If a block reads \(x\) and then writes \(x\), \(x\) is in use, not in def, because the read happens first. If it writes \(x\) and then reads \(x\), \(x\) is in def, and the later read does not make the incoming value live. Getting this order wrong flips the liveness result.

10.6 Available expressions

An expression \(e\) is available at a point if every path from entry to that point evaluates \(e\), and no operand of \(e\) is redefined after the evaluation. This is a forward must analysis: “every path” means intersection. It is the basis for global common-subexpression elimination.

For each block \(B\):

  • \(\mathrm{gen}[B]\): expressions that are definitely computed in \(B\) and still available at the end of \(B\).
  • \(\mathrm{kill}[B]\): expressions with an operand defined in \(B\). If an expression is killed and then recomputed, it is in both sets; the equation re-adds it through gen.

The equations are:

\[ \mathrm{IN}[B]=\bigcap_{P\in\mathrm{pred}(B)}\mathrm{OUT}[P],\qquad \mathrm{OUT}[B]=\mathrm{gen}[B]\cup(\mathrm{IN}[B]-\mathrm{kill}[B]). \]

For the entry block, \(\mathrm{IN}[\text{entry}]=\varnothing\) and \(\mathrm{OUT}[\text{entry}]=\mathrm{gen}[\text{entry}]\). For every other block, initialize \(\mathrm{OUT}[B]\) to the universal set \(U\) of all expressions, then iterate downward by intersection. Starting at the top and moving down computes the greatest fixed point, which is the most precise safe set of guaranteed-available expressions.

10.7 Global common-subexpression elimination

Available expressions tells you where an expression is guaranteed to have been computed. Global CSE uses that fact to replace a recomputation with a use of the earlier value. The replacement is safe when:

  • the expression is available at the point (every path computed it);
  • a single temporary or variable holds that value on every path, or the compiler inserts a merge/phi to name it;
  • no side effect or aliasing write has changed the operands since the computation;
  • the expression is pure (or the language guarantees the same result and exceptions).

In a structured program where one computation dominates the later one, the dominating temporary is the natural representative. In a general CFG, the earlier computation may be in different blocks on different paths. A compiler can still perform CSE by introducing a fresh temporary and inserting copies or phi functions at the joins, or by working on SSA form, where each value has one definition and the merge is explicit.

The easy case. If B1 computes t1 = a + b and B5 is reached only through B1, with no redefinition of a or b, then t3 = a + b in B5 can become t3 = t1. The available-expression analysis proves the value is still current; the dominating definition supplies the name. In the branch example above, the path through B4 breaks the proof, so the replacement is not safe without a merge.
Key. Reaching definitions: forward may, union, “which definitions can get here?” Live variables: backward may, union, “which values will be used later?” Available expressions: forward must, intersection, “which expressions are already computed on every path?” Constant propagation: forward, lattice meet, “which variables have the same constant on every path?”
Heads-up: available expressions is not the same as “the expression was computed somewhere before.” It must be computed on every path, and its operands must not be redefined afterward. A computation in one branch does not make the expression available after the branch joins.
Heads-up: global CSE needs a name for the shared value. Knowing that \(a+b\) is available does not by itself say which temporary holds it. If the computations are in different blocks, you may need a merge (phi) or a fresh temporary. “Available” is the proof of safety; naming is a separate implementation problem.

10.8 Constant propagation

Constant propagation asks: at this point, does variable \(x\) have the same constant value on every path? If yes, replace uses of \(x\) by that constant and fold the arithmetic. It is a forward analysis over the constant lattice from Section 10.2: \(\top\) means “no information,” a constant \(c\) means “definitely \(c\),” and \(\bot\) means “not a constant” because paths disagree or the value is unknown.

The transfer function for a block is straightforward:

  • x = c: set \(x\) to \(c\).
  • x = y: copy \(y\)’s value.
  • x = y op z: if both operands are constants, evaluate the operation; otherwise set \(x\) to \(\bot\).
  • Any other variable keeps its incoming value.

At a join, take the meet: \(\top\sqcap c=c\), \(c\sqcap c=c\), and \(c\sqcap d=\bot\) for \(c\neq d\). Parameters and external inputs start at \(\bot\) (they can be anything); locals start at \(\top\) until assigned. The iteration moves downward from \(\top\) toward constants or \(\bot\).

Constants that survive a branch. 
B1: x = 1
B2: if p goto B3 else B4
B3: y = 2
    goto B5
B4: y = 2
    goto B5
B5: z = x + y
At B5, \(x=1\) on both paths, and \(y=2\) on both paths, so \(z=3\). The meet of \(2\) and \(2\) is \(2\), not \(\bot\). If B3 assigned \(y=3\) instead, the meet at B5 would be \(2\sqcap3=\bot\), and \(z\) would not be constant. The condition \(p\) is irrelevant: constant propagation does not need to know which branch is taken when both branches agree.
A loop kills a constant. If \(x=1\) before a loop and the loop body assigns \(x=2\), then at the loop header the incoming value from the preheader is 1 and the value on the back edge is 2. The meet is \(\bot\). Even though the first iteration sees 1, the analysis must be correct for every iteration, so \(x\) is not a constant at the header. This is the data-flow version of “one assignment is not enough; every path must agree.”

Sparse conditional constant propagation (SCCP) goes further: it tracks which CFG edges are executable. If a branch condition is constant, only the feasible edge is considered, and values from the unreachable edge do not pollute the meet. This can discover constants that plain propagation misses, and it can prove branches dead. The price is a more complex algorithm that couples constant values with reachability.

Heads-up: folding a trapping operation can change behavior. If x/0 would raise an exception or terminate the program at run time, replacing it with a compile-time error or a arbitrary value is not semantics-preserving. Fold only when the language guarantees the operation is safe, or when the exceptional behavior is preserved. The same caution applies to overflow and to floating-point exceptions.

10.9 Dominators and loops

Many optimizations need to know which blocks are inside a loop and which block controls entry to another. The foundation is dominance. A block \(d\) dominates a block \(n\) if every path from entry to \(n\) passes through \(d\). Every block dominates itself, and the entry dominates every reachable block.

Dominators are a forward must analysis over sets of blocks:

\[ \mathrm{Dom}(\text{entry})=\{\text{entry}\},\qquad \mathrm{Dom}(n)=\{n\}\cup\bigcap_{p\in\mathrm{pred}(n)}\mathrm{Dom}(p). \]

Initialize \(\mathrm{Dom}(n)\) to the set of all blocks for \(n\neq\text{entry}\), then intersect downward. The immediate dominator \(\mathrm{idom}(n)\) is the closest strict dominator of \(n\); the edges \(n\to\mathrm{idom}(n)\) form the dominator tree.

Dominators on a loop. CFG: \(B_1\to B_2\), \(B_1\to B_3\), \(B_2\to B_4\), \(B_3\to B_4\), \(B_4\to B_5\), \(B_5\to B_4\).
BlockDominatorsImmediate dominator
B1{B1}—
B2{B1,B2}B1
B3{B1,B3}B1
B4{B1,B4}B1
B5{B1,B4,B5}B4
The edge \(B_5\to B_4\) is a back edge because \(B_4\) dominates \(B_5\). The natural loop of that back edge is the header \(B_4\) plus every block that can reach \(B_5\) without passing through \(B_4\): here \(\{B_4,B_5\}\). \(B_4\) is the loop header; \(B_5\) is the latch.

A preheader is a new block inserted before the loop header, with a single edge to the header and no other predecessors. It gives loop-invariant code a safe place to execute once, before the loop. Loop-invariant code motion moves an instruction out of the loop if its operands do not change in the loop, it has no side effects, moving it does not introduce a trap on a path that would not have executed it, and the definition dominates all uses. The safety conditions matter: moving a division out of a loop can turn a program that never divides by zero into one that does.

Strength reduction in loops often uses induction variables: variables that change by a fixed amount each iteration. If i increases by 1 and A[i] is addressed as base + i*w, a new pointer p can start at base and increase by w each iteration. The multiplication disappears, and the loop has one fewer expensive operation.

11. The Superpowers toolkit

Forty moves, in the order you will need them. Each one is a mechanism, not a slogan.

  1. Draw the pipeline first. Source → tokens → tree → typed tree → IR → optimized IR → target. Label what each arrow hands on. Most “which phase?” questions answer themselves once the handoffs are visible.
  2. Separate token, lexeme, pattern. Token = class; lexeme = actual characters; pattern = regular expression describing the class. Attributes carry the identifier’s symbol-table pointer or the number’s value.
  3. Apply longest match, then rule order. The lexer takes the longest prefix that matches any rule; ties go to the earlier rule. This is why >= beats > and keywords beat identifiers.
  4. Remember regex precedence. Star binds tightest, then concatenation, then union. Parenthesize when in doubt; \(ab^*|c\) is not \((ab)^*|c\).
  5. Build an NFA with five shapes. Symbol, epsilon, union, concatenation, star. Thompson gives \(O(|r|)\) states and a single start/accept pair.
  6. Convert NFA to DFA with closure + move. A DFA state is a set of NFA states; start at \(\varepsilon\text{-closure}(q_0)\); accept if the set contains an NFA accept state.
  7. Minimize by splitting blocks. Start with accepting/non-accepting; split when a symbol sends states to different blocks; repeat. Do not merge states just because they share a label.
  8. Use the regular/context-free boundary. Regex cannot count arbitrary nesting; a stack (parser) can. Comments with nesting, balanced brackets, and indentation blocks are parser territory.
  9. Say “grammar generates, parser recognizes.” A derivation is a proof; a parse tree is the grouping; leftmost/rightmost is only an order.
  10. Test ambiguity with two trees. If one terminal string has two parse trees (or two leftmost derivations), the grammar is ambiguous. The language may still have another, unambiguous grammar.
  11. Encode precedence by layering, associativity by recursion. \(E\to E+T\mid T\), \(T\to T*F\mid F\) makes * tighter and + left-associative. The tree does the work; no extra precedence rule is needed.
  12. Resolve dangling else structurally. Either use the matched/unmatched grammar or accept the default “else binds to the nearest unmatched if.” Do not leave the ambiguity implicit.
  13. Compute FIRST upward. Terminals give themselves; a nonterminal collects FIRST of its alternatives; a string collects FIRST of the first symbol and continues through nullable symbols; add \(\varepsilon\) only if the whole string is nullable.
  14. Compute FOLLOW from the start. Put \(\$\) in FOLLOW(S); for \(A\to\alpha B\beta\), add FIRST(\(\beta\)) minus \(\varepsilon\); if \(\beta\) is nullable, add FOLLOW(A). FOLLOW never contains \(\varepsilon\).
  15. Test LL(1) by the table. One production per cell. Alternatives need disjoint FIRST sets; a nullable alternative needs disjointness with FOLLOW. “No left recursion and no common prefix” is necessary but not sufficient.
  16. Kill left recursion mechanically. \(A\to A\alpha\mid\beta\) becomes \(A\to\beta A'\), \(A'\to\alpha A'\mid\varepsilon\). For indirect recursion, order the nonterminals and substitute in order.
  17. Left-factor common prefixes. \(A\to\alpha\beta_1\mid\alpha\beta_2\) becomes \(A\to\alpha A'\), \(A'\to\beta_1\mid\beta_2\). Delay the choice until the lookahead can make it.
  18. Run an LL(1) parser with a stack. Top nonterminal + lookahead → table entry; push the right side reversed; match terminals; accept at \(\$\). \(\varepsilon\)-productions are chosen on FOLLOW.
  19. Tell the LR story. Left-to-right scan, rightmost derivation in reverse, stack holds a viable prefix, handle on top, reduce it. The table decides shift, reduce, accept, error.
  20. Build LR(0) items with closure and goto. Dot = progress. Closure adds productions for the nonterminal after the dot; goto moves the dot over a symbol. Completed items are reduction candidates.
  21. Use FOLLOW for SLR. Reduce \(A\to\alpha\) only on tokens in FOLLOW(A). If a state also shifts one of those tokens, SLR has a conflict; the grammar may still be LR(1).
  22. Use exact lookahead for LR(1). An item \([A\to\alpha\cdot\beta,a]\) reduces only on \(a\). Closure computes \(b\in\text{FIRST}(\beta a)\). LALR merges same-core states and unions lookaheads; this can create reduce/reduce conflicts but not new shift/reduce ones.
  23. Keep the power order straight. LR(0) ⊂ SLR(1) ⊂ LALR(1) ⊂ LR(1). Stronger means more grammars handled without conflicts, not more languages.
  24. Resolve conflicts deliberately. Rewrite the grammar, add precedence/associativity, or choose a default and document it. On shift/reduce: higher token precedence shifts, lower reduces, equal uses associativity.
  25. Distinguish synthesized from inherited. Synthesized comes from children and flows up; inherited comes from the parent or left siblings and flows down/sideways. Annotate the tree; do not guess.
  26. Use S for bottom-up, L for top-down. S-attributed = synthesized only, evaluate at reductions. L-attributed = inherited only from the parent/left siblings, evaluate left-to-right depth-first.
  27. Write 3AC with one operator per instruction. Quadruples: op, arg1, arg2, result. Triples: result by position. Indirect triples: a reorderable pointer table.
  28. Backpatch forward jumps. Keep true/false/next lists; makelist, merge, backpatch. For if, patch the true list to the then-start and merge the false list into next; for while, patch the body’s next list to the condition and the false list to the exit.
  29. Use a DAG or value numbering for local CSE. Hash (operator, operand value numbers); identical keys are the same computation. Reuse the earlier result if operands have not changed and the operation is pure.
  30. Check types by structure, name, or inference. Structural equivalence compares shape; name equivalence compares declarations; unification solves type equations with an occurs check. Insert coercions only where the language allows them.
  31. Draw the activation record. Parameters, return address, saved registers, access link, control link, locals, temporaries. Access link → lexical parent; control link → caller. Static scope follows access links; dynamic scope follows control links.
  32. Know the parameter modes. Value copies; reference aliases; value-result copies in and out; name re-evaluates each use; need memoizes. Aliasing makes swaps and copy-out order tricky.
  33. Find leaders, then blocks. First instruction; jump targets; instructions after jumps. A block is a leader to the next leader minus one. Edges are possible control transfers; the result is the CFG.
  34. Run the local checklist. Fold constants, propagate copies and constants, apply safe identities, reduce strength, eliminate dead code, reuse common subexpressions, then peephole. Check side effects and exceptional behavior every time.
  35. Ask the data-flow four questions. Direction? May or must? Transfer (gen/kill)? Initial value? Then write IN/OUT equations and iterate to a fixed point.
  36. Recognize the four core analyses. Reaching definitions: forward may union, gen/kill definitions. Live variables: backward may union, use/def. Available expressions: forward must intersection, gen/kill expressions. Constant propagation: forward lattice meet, \(\top\)/constant/\(\bot\).
  37. Initialize for the fixed point you want. May analyses start at bottom (empty) and move up; must analyses start at top (universal) and move down. Entry/exit boundary conditions are part of the analysis, not an afterthought.
  38. Use liveness for registers and dead code. Two variables interfere if both are live at one point. A definition is dead if its target is not live immediately after it and the instruction has no other effect.
  39. Use available expressions for global CSE. The expression must be computed on every path and its operands unchanged. Then supply a name for the shared value — a dominating temporary, a merge, or an SSA phi.
  40. Find loops with dominators. A back edge \(n\to h\) has a header \(h\) that dominates \(n\); the natural loop is \(h\) plus nodes that reach \(n\) without passing \(h\). Use a preheader for loop-invariant motion, and check traps and side effects before moving code.
